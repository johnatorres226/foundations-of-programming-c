Module 0 · Chapter 4

Set Up Your Machine

Last chapter you learned to name the versions of C — C89, C99, C11, C17, and C23 — and what changed between them. You also learned why this course picks C17 to write in, even though C23 is the newest standard: not every compiler supports C23 well yet, and a beginner should not have to debug a standard-version mismatch.

Big picture: why nothing runs until a compiler is installed

You cannot run C code by opening it, the way you open a photo or a text document. A computer only runs a special kind of file made of instructions it understands directly. A compiler is a program that reads the C code you write and turns it into that kind of file. Every chapter after this one asks you to write C code and run it — none of that works until a compiler is installed on your own computer.

Chapter 0.1 called this trade-off directly: a computer's CPU only understands machine code, and a compiled language like C needs something to do that translation before your program can run at all. A compiler is that something. Think of it like needing a working oven before you can bake a cake from a recipe — the recipe (your C code) is correct and complete, but it stays a piece of paper until something actually turns it into food. No working oven, no cake, no matter how good the recipe is.

Some languages hide this step from you. Open certain websites and you can type code into a box in your browser and watch it run immediately, with nothing installed at all. This course does not take that shortcut on purpose. Installing a real toolchain on your own computer, once, means every program you write from here on is a real file you own, that runs the same way whether or not you have internet access — and it means you understand what "running a program" actually involves, instead of trusting a website to hide it from you.

This chapter's own page follows the same rule it is asking of you. Every lesson in this course opens straight from a file on your computer, with no internet connection required — you could turn off your wifi entirely right now and keep reading. The course asks you to set up a compiler that works the same way: installed once, working offline, answerable only to you. That consistency is not an accident; it is the same "own your tools" idea applied twice, once to how you read this course and once to how you run the code you write for it.

Before you can write and run any C program, you need a compiler installed on your own computer.

How it works

A compiler is one part of a bigger set of tools called a toolchain — the compiler plus the other small programs it needs to turn your code into a program you can run. You install the whole toolchain at once. You will type the install commands into a terminal — a window where you type commands instead of clicking buttons. Find the section below for your operating system.

Getting the course files onto your computer

Every exercise in this course is a real file, meant to live on your own computer, not inside a website. Before anything below, you need your own copy of this course's files sitting somewhere on your hard drive. There are two ways to get one.

The simplest way needs no extra software: on the course's GitHub page, click the green "Code" button, then "Download ZIP." Your browser downloads a single compressed file. Open it — double-click on macOS and Windows, or use your file manager's "extract" option on Linux — and you have a normal folder full of the course's files, including this very page.

The way most working programmers actually use is a tool called Git — software for tracking changes to a project's files over time, covered properly in a later module. For now you only need one command, once Git itself is installed (macOS and Linux normally already have it; Windows users following the WSL path above already installed it as part of that):

$ git clone https://github.com/johnatorres226/foundations-of-programming-c.git
$ cd foundations-of-programming-c

git clone downloads the whole project into a new folder named after the repository. The second command moves your terminal's current directory into it — the first real use of cd you will make in this course, and the same command the next section explains properly.

Either way, you now have a folder that matches the file paths this course refers to throughout — src/modules/..., assets/..., and so on. The rest of this chapter assumes you are inside that folder, or know how to reach it, before you start compiling anything.

If double-clicking a downloaded CONTENT.html file shows raw text full of < and > symbols instead of a formatted page, it opened in a text editor instead of a web browser. Right-click the file and choose "Open with," then pick your browser instead.

Opening a terminal and finding your files

Every step below assumes you already have a terminal open and know how to reach the folder that holds your files. A terminal only runs the exact command you type — it does not guess what you mean, and it does not know where your files are unless you tell it. Get comfortable with these few ideas first, and every install step below will make more sense.

When a terminal opens, it shows a short line of text followed by a blinking cursor. That line is called a prompt — it means the terminal is idle and waiting for you to type a command. This course shows a prompt as a plain $ in every terminal example, the same as you have already seen in this chapter. Your own terminal's prompt will look different — it might show your username, your computer's name, or a folder name — but the $ in this course always means "wherever your own prompt is, type this next."

A terminal always has one folder it is "in" at any moment, called its current directory. Every plain filename you type — hello.c, for example — is understood relative to that folder. Two commands you will use constantly:

$ pwd
/Users/yourname/foundations-of-programming-c
$ ls
CONTRIBUTING.md  README.md  SYLLABUS.md  assets  src  ...

pwd ("print working directory") shows the current directory's full path. ls ("list") shows the files and folders inside it. To move into a folder, use cd ("change directory") followed by its name:

$ cd src/modules/0-module-intro/4-chapter-set-up-your-machine/exercises
$ ls
hello.c

That is the exact folder this chapter's exercise file lives in, once you have cloned the course onto your own computer. Every "open a terminal and run" instruction from here on assumes you have already used cd to reach the right folder — usually the one holding the file you are about to work on.

"File not found" or "No such file or directory" almost always means your terminal's current directory is not where you think it is — not that the file itself is missing. Run pwd to check where you actually are, and ls to see what is actually there, before you go looking for another explanation.

One more thing before you install anything: this course's Windows path (MSYS2 or WSL, both covered below) gives you a terminal that understands pwd, ls, and cd exactly like macOS and Linux do. You will not need separate Windows-only versions of these commands anywhere in this course.

macOS

Apple ships a compiler as part of a small package called the Command Line Tools. To open a terminal, press Cmd + Space to open Spotlight — a search box built into macOS — type "Terminal," and press Enter. A new window opens with a prompt waiting for you. In it, run:

$ xcode-select --install

A window pops up asking you to confirm. Click install, and wait — it can take a few minutes, since it downloads several hundred megabytes over your internet connection. This gives you clang, a compiler that also understands the cc command used throughout this course — on macOS, cc and clang are two names for the exact same program.

Some macOS tutorials elsewhere online instead recommend installing a separate compiler through Homebrew, a popular package manager for macOS. You do not need Homebrew for this course — the Command Line Tools already give you everything these chapters ask for. If you already have Homebrew installed for other reasons, that is fine too; nothing here conflicts with it.

If xcode-select --install reports that the Command Line Tools are already installed, you already have a working compiler — there is nothing else to do here. You do not need the full Xcode app for this course. Xcode is a much larger download from the App Store, meant for building iPhone and Mac apps with a graphical editor; the Command Line Tools it is built from are the only part a C course needs.

Linux

Linux comes in many distributions (often shortened to "distros") — different companies and communities package the same underlying operating system with their own set of tools and their own package manager, a program for installing and updating software from the command line. Which command you run depends on your distribution, but all of them install the same three things: a compiler, make (a tool later chapters use to build multi-file programs), and the standard library headers.

On Ubuntu, Debian, and most distributions built on them, one package installs all three at once. Open a terminal and run:

$ sudo apt update
$ sudo apt install build-essential

sudo ("superuser do") runs the command with permission to change system files — installing software needs that permission, which is why it asks for your password. apt update refreshes the list of available software versions first, so apt install fetches a current one rather than something outdated.

On Fedora, the same toolchain comes from a differently named group of packages:

$ sudo dnf groupinstall "Development Tools"

On Arch Linux and its derivatives (Manjaro, EndeavourOS), it is one package named for exactly what it is — the base tools every piece of software on the system is built with:

$ sudo pacman -S base-devel

All three commands above install the same kind of toolchain under a different package name, because apt, dnf, and pacman are three different package managers for three different distribution families. Once installed, the compiler itself works identically no matter which one you used to get it.

If sudo apt install reports "Permission denied" or asks for a password you do not have, you are not logged in as an account allowed to install software on this machine — a shared school or work computer, for example. Ask whoever manages the machine to run the install command, or use a personal computer instead. If your distribution is not Ubuntu, Debian, Fedora, or Arch (or built on one of them), search "<your distribution name> install gcc" — nearly every Linux distribution ships some package named something like gcc or build-essential.

Windows

Windows has no C compiler built in, so you have two options. Both give you a real, working compiler; they differ in what kind of terminal and environment you end up typing your commands into.

Choose MinGW-w64 if you want to stay inside Windows itself, with no second operating system involved — a lighter install, and the compiled programs it produces are ordinary Windows .exe files you could hand to any other Windows user. Choose WSL if you would rather follow this course's Linux instructions directly, word for word, or if you expect to work with Linux servers or tools later — WSL is a real, complete Linux system, not an imitation of one, running alongside Windows.

Option A — MinGW-w64. This installs a real Windows compiler, MinGW-w64, through a package manager called MSYS2. Install MSYS2 from msys2.org, then open the "MSYS2 UCRT64" terminal from your Start menu and run:

$ pacman -S mingw-w64-ucrt-x86_64-gcc

Option B — WSL. WSL (Windows Subsystem for Linux) runs a real Linux system inside Windows. If you would rather follow the Linux instructions above, open PowerShell as an administrator and run:

$ wsl --install

Restart your computer when it asks. Then open the new Ubuntu app it installed and follow the Linux steps above inside it.

If your terminal says something like command not found: cc or 'gcc' is not recognized, the install did not finish, or you opened the wrong kind of terminal window. On Windows, MinGW-w64 commands only work inside the MSYS2 UCRT64 terminal, not the regular Command Prompt. Closing and reopening your terminal after install fixes most cases — the terminal only reads where to find your compiler when it starts up.

Two more Windows-specific traps. wsl --install can fail on older Windows 10 builds with a message about a missing feature — Windows Subsystem for Linux has to be turned on first, under Settings → Apps → Optional features → More Windows features → "Windows Subsystem for Linux." And if MSYS2's pacman command itself says "not recognized," you opened a regular Windows terminal instead of one of the MSYS2-specific terminals MSYS2 added to your Start menu — pacman only exists inside those.

Choosing a text editor

The other tool you need, besides a compiler, is a text editor — a program for writing plain text with no hidden formatting. A word processor like Microsoft Word will not work here: it saves hidden styling information alongside your words, and a compiler cannot make sense of any of that. Every option below saves plain text, and every option is free.

  • Visual Studio Code (code.visualstudio.com) — runs on macOS, Linux, and Windows, and is the most common choice for beginners. Its built-in terminal panel means you can edit and run your program without switching windows. Its optional "C/C++" extension adds colored syntax highlighting for C code specifically, which makes typos like a missing quotation mark easier to spot at a glance — install it from the Extensions panel (the icon of four squares in the left sidebar) if you want it, but nothing in this course requires it.
  • Whatever came with your computer. TextEdit on macOS works once you switch it to plain text (Format → Make Plain Text — its default mode adds hidden formatting). Notepad on Windows is plain text already.
  • nano, a small editor that opens directly inside the terminal, already installed on macOS, Linux, and inside WSL. Its own commands are listed at the bottom of the screen — a fine choice if you are already comfortable in a terminal.

None of these is required by this course specifically — pick whichever one you find least confusing to open and save a file in. You will use it for every chapter from here on, so it is worth spending five minutes making sure you can open a specific file, change it, and save it, before moving on to compiling anything. Whichever you pick, make sure it saves files with a plain .c ending, not .c.txt or .rtf — some editors quietly add their own extension unless you tell them not to, and a compiler that cannot find hello.c because it is actually named hello.c.txt will report a confusing error that has nothing to do with your actual code.

On macOS, if you open hello.c in TextEdit and the compiler rejects it with strange errors even though the text looks right, TextEdit likely saved it in its default rich text format instead of plain text. Format → Make Plain Text, then save again, fixes it.

Compile and run your first program

Chapter 0.3 explained why this course writes C17 code. That is why -std=c17 appears in every compile command you will see, starting now. Each of these dash-prefixed pieces is called a flag — an instruction to the compiler about how to do its job, separate from your actual code. This course always uses the same four:

  • -std=c17 — use the C17 rulebook (chapter 0.3), nothing newer.
  • -Wall — turn on the compiler's most common warnings: code that compiles but is almost always a mistake.
  • -Wextra — turn on a second, stricter set of warnings that -Wall does not cover by itself.
  • -Werror — treat every warning as an error, so the compiler refuses to finish until you fix it, instead of letting you shrug one off and move on.

Turning on warnings from day one catches mistakes while they are still small — a warning your compiler tries to tell you about now is a bug you would otherwise have to hunt down by hand later.

#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}

#include and printf are covered token by token next chapter. For now, open a terminal in the folder that holds hello.c and run:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
$ ./hello
Hello, C!

The first command compiles: it reads hello.c and writes a brand new file to the same folder, named hello because of the -o hello flag (-o for "output" — leave it off and the compiler names the file something less useful, like a.out). Run ls in that folder right after compiling and you will see a file that was not there a moment ago. That new file is not source code you can open and read — it is machine code (chapter 0.1), built specifically for the computer you compiled it on.

The second command, ./hello, runs that new file. The ./ in front means "look for this program in the current directory," rather than in one of the places your computer normally looks for already-installed programs — a habit your terminal expects of you, not something specific to C. If you see Hello, C! printed back, your toolchain works. (On Windows with MinGW-w64, the compiled file is named hello.exe, and you run it with hello instead of ./hello.)

Checking your install: PATH and version

Every "command not found" gotcha above has the same real cause. When you type cc, your terminal does not search your whole computer for a program with that name — it only checks a specific list of folders called your PATH. Installing a compiler normally adds its folder to that list automatically. If it does not — or if you opened a terminal before the install finished updating it — cc is not "broken," it has not been added to any folder your terminal currently knows to look in. That is why closing and reopening your terminal fixes most install problems: a new terminal window reads your PATH fresh.

Two commands you can run anytime to sanity-check your setup, once install finishes:

$ cc --version
Apple clang version 17.0.0 (clang-1700.0.13.5)
Target: x86_64-apple-darwin24.6.0
$ which cc
/usr/bin/cc

cc --version prints which compiler you actually have and its exact version — the numbers on your own machine will not match the example above, and that is fine; any reasonably recent version compiles this course's C17 code correctly. which cc prints the exact file your terminal runs when you type cc. If either command fails with "not found," the install did not finish, or your PATH does not include it yet — reopen your terminal, and if that does not help, re-read the install steps for your operating system above. Keep both commands in mind for the rest of the course: whenever something that used to work suddenly reports "command not found," this is the first place to look, long before assuming your own code is at fault.

Install the toolchain for your operating system above. Then open exercises/hello.c and compile and run it yourself:

  • exercises/hello.c — the exact program shown above, ready to compile

Module 0 has no automated tests. Check your work by eye: if your terminal prints Hello, C!, your setup is done. If it prints an error instead, re-read the gotcha box above for your operating system.

Zooming out: from a working toolchain to reading your first program

You now have a working C toolchain — the one thing every later chapter assumes you already have. That is the last setup step in this course; from here on, every chapter is about the language itself. Notice that you actually installed three separate tools, not one: a terminal to type commands into, a text editor to write source code in, and a compiler to turn that source code into something the computer can run. Keeping those three jobs separate, instead of hiding them inside one all-in-one program, is exactly the same C philosophy from chapter 0.1 — nothing is hidden from you that you have not chosen to trust.

Next chapter you will take the exact program you already compiled and read it token by token: what #include, main, return, and printf each do, and why every C program needs them in that order. You will keep using the same three tools — terminal, editor, compiler — for the rest of the course; only the code you write in them gets more interesting from here.

If anything in this chapter did not work on the first try, that is normal, not a sign you did something wrong. Toolchain setup is one of the few genuinely fiddly parts of learning C, precisely because it depends on your specific computer, and the gotcha boxes above cover the failures learners hit most often. Once exercises/hello.c compiles and runs cleanly for you, this chapter is done for good — you will not have to repeat any of it for the rest of the course.
