Last chapter you learned what a CPU does, what source code is, and the difference between a compiled language and an interpreted one. C is a compiled language. This chapter tells you where C came from, what problem it was built to solve, and why it spread so far.

Big picture: the portability problem C was built to solve

Before C, moving a program to a different computer often meant rewriting it from scratch. Programs were written in assembly language — instructions written for one exact kind of computer chip, using that chip's own private vocabulary. An assembly program written for one machine would not run on a different one at all.

That was a real problem for the people building operating systems — the software that manages a computer's hardware and lets other programs run on it. Every new computer meant starting the operating system over. C was built to end that. Knowing why explains a lot of what C still looks like today: a language close enough to the hardware to be fast, but written in a way that could move to a new machine without a full rewrite.

Picture two computers built by two different companies in 1970. Each used its own kind of processor chip, and each chip understood its own private list of instructions. An assembly program written for one chip was a list of instructions in that chip's own language — it made no more sense to the other computer than a page of Japanese makes to someone who has only ever read English. Moving the program to the second computer meant a person sitting down and rewriting every single instruction by hand, for a completely different private language. That is the wall C was built to knock down.

This was not a small inconvenience. For a company running its business on a computer, replacing that computer with a newer, faster model could mean months — sometimes longer — of programmers rewriting software that already worked, one instruction at a time, only to say the same thing in the new machine's private language. None of that time added a single new feature. It only bought back what the company already had before the upgrade. Any language that could remove that tax, without giving up real speed, was worth building.

The exact shape of the problem has changed since the 1970s, but a version of it is still around you today. A phone app has to be built differently depending on whether it runs on an iPhone or an Android phone. A desktop program often needs separate work to run on Windows, macOS, and Linux. Programmers still spend real time and money bridging differences between machines — it is a smaller gap than "completely different private language" now, in large part because languages like C proved that gap could be narrowed at all.

C exists because two programmers at Bell Labs needed a language almost as fast as assembly, but able to move to a new computer without starting over.

How it works

Before C: one machine, one language

Bell Labs, where this story starts, was the research arm of AT&T, the American telephone company. It was not primarily a software company — it is better known for inventing the transistor, the tiny electronic switch that every computer chip since has been built from. A research lab full of engineers focused on hardware, given time and freedom to explore, is exactly the kind of place a project like Unix could start as a side effort rather than an official assignment.

In the early 1970s, Ken Thompson and Dennis Ritchie worked at Bell Labs, a research company in the United States. They were building an operating system called Unix. The first version of Unix was written in assembly language for one specific computer, a PDP-7. It worked, but it was stuck on that one machine, for exactly the reason the big picture above described: its instructions were written in that one chip's own private language.

Thompson first tried a simpler language called B, based on an older language named BCPL, to escape that trap. B was easier to move between computers than assembly language, because a B compiler could be written for a new machine once, instead of rewriting a whole program by hand every time. But B was too limited for the job it needed to do next. It had no real way to work with different kinds of data — B treated a whole number, a single character, and a fraction all the same way, as one generic kind of value. Writing an operating system means talking directly to a computer's hardware, and hardware cares a great deal about exactly how big a piece of data is and what kind it is. B could not say that precisely enough.

Before any of this, Bell Labs had been part of a much bigger, more ambitious project called Multics, built together with MIT and General Electric, aiming to build an operating system many people could share at once. Bell Labs pulled out of Multics in 1969 — the project had grown too large and too slow to finish. Thompson and Ritchie carried some of Multics's ideas about how an operating system should be organized into a small, much simpler system they built themselves, on a spare PDP-7 nobody else at Bell Labs was using at the time. They picked a name that poked fun at the project they had recently left behind: Unix.

The push to actually get that PDP-7 working came from something almost beside the point: Thompson had written a space-flight game, and he wanted to keep playing it once Bell Labs' access to the Multics computer it ran on disappeared. Getting the game running on the idle PDP-7 meant first building enough of an operating system underneath it to load and run any program at all. The game motivated the work; the small operating system that came out of it, refined and rewritten over the next few years, is the Unix this chapter is about.

BCPL, B, and C sound like a tidy chain of upgrades, but each one was closer to a fresh rewrite than an update. An old B program does not compile as C without changes — C's rules about data types are stricter, on purpose, than anything B ever checked.

From B to C (1971–1973)

Between 1971 and 1973, Ritchie extended B with the missing pieces: a real way to say "this is a whole number," "this is a single character," or "this is a decimal number," and have the compiler hold you to it. Those became C's basic types — int for whole numbers and char for single characters are two you will use in the very next chapter. The result of Ritchie's work was different enough from B that it needed its own name: C — the letter after B, in the BCPL-to-B-to-C lineage.

Ritchie's changes went further than types alone. He also gave C a way to talk about a variable's memory address directly, instead of only its value — the beginning of what this course calls pointers much later, in Module 5. And he gave C a way to bundle several related pieces of data together under one name — the beginning of what this course later calls a struct, in Module 6. Neither term needs to mean anything to you yet; both get their own chapter and their own real definition when the time comes. What matters now is that both were built into C from nearly the start, because an operating system needs to describe raw memory and grouped hardware data precisely — exactly the two things B could not do.

The 1973 Unix rewrite

The turning point came when Thompson and Ritchie rewrote most of the Unix operating system itself in C, finishing by 1973. At the time, this was close to unheard of. The common wisdom was that an operating system's core had to be written in assembly language, because only assembly was considered fast and direct enough to manage a computer's hardware. Rewriting Unix in C was a bet that a language with real data types and a compiler standing between the programmer and the machine could still do that job. The bet paid off, and it made Unix one of the first operating systems in history whose core was not written in assembly language.

To see how unusual that was, look at what large companies were shipping at the same time. IBM's mainframe operating systems of that era, running on the machines many banks and airlines depended on, were written almost entirely in assembly language for IBM's own hardware — the standard approach everywhere else. Unix, built by a small team at a research lab rather than a large company's product division, took the opposite bet and won it.

The rewrite did not remove assembly completely. A small amount stayed — mainly the handful of places where the operating system starts up for the first time, or reacts to a hardware signal in a way too specific to one exact chip's wiring for even C to describe. That same split still holds in modern operating system kernels today: the vast majority is written in a higher-level language like C, with a thin, deliberately small layer of hand-written assembly underneath it for the handful of jobs that need it.

Rewriting an operating system in C did not make it slow. C was designed to compile down to instructions almost as direct and fast as assembly language — the trade C made was giving up assembly's dependence on one exact computer, not giving up speed.

Why C and Unix spread together

That rewrite is why C and Unix spread together. A computer maker who wanted to run Unix on new hardware no longer needed to rewrite an entire operating system by hand. Someone had to write a new C compiler — a program that turns C source code into instructions a specific computer can run — for that hardware, and most of Unix's own code could then move over with little or no change. Software that can move to a new computer like this is called portable.

Portability like this tends to feed on itself. Every new computer that got a C compiler was one more machine where existing C programs — Unix included — could run with little extra work. That made C a safer bet for the next hardware maker deciding which language to support, since a growing pool of software already existed for it. Each new compiler made the next one more worthwhile to write. None of that required a company or a committee to plan it that way — it fell out naturally from the fact that a program written once could now be useful on more than one machine.

Word of the rewrite spread beyond Bell Labs largely through one paper: Ritchie and Thompson published "The UNIX Time-Sharing System" in 1974, describing what they had built and, notably, that most of it was written in a language other researchers could get a compiler for. Universities and labs that read it wrote to Bell Labs asking for a copy of the actual system, not only the description of it.

Unix had another push behind it, too. Bell Labs' parent company, AT&T, was bound by an old legal restriction that kept it from selling Unix as a commercial product. So instead of selling it, AT&T licensed Unix's source code to universities for barely more than the cost of the tape it shipped on. Computer science departments across the United States got a real, working operating system to study, teach with, and improve — and because it was portable, each university's own hardware could run it. Students who learned Unix and C in school carried both languages into the companies they joined next.

The University of California, Berkeley, is the clearest example of what that "improve" meant in practice. Researchers there did not only run the Unix source code AT&T licensed them — they modified it, added their own features, and eventually distributed their own version, known as BSD (Berkeley Software Distribution). BSD and AT&T's own Unix grew into separate, related family trees, both still written in C, both descended from the same 1973 rewrite. Versions of that Berkeley lineage are still running today, inside Apple's macOS among other systems.

Portable does not mean "runs unmodified on absolutely anything." Some code — the parts that talk directly to one machine's specific hardware — still has to change for each new computer. Portable means the vast majority of a program does not have to change, which is a very different, much better place to start from than rewriting everything.

By the 1980s, C had become useful enough on its own that it no longer needed Unix to spread. Compiler makers wrote C compilers for computers that had nothing to do with Unix at all, including the IBM PC and the home computers many people had recently started buying. A company called Borland sold a C compiler named Turbo C that a huge number of 1980s programmers learned from, on machines running Microsoft's MS-DOS, not Unix. By this point, C had grown from "the language Unix happens to be written in" into a language people reached for on its own merits.

The book that taught everyone (1978)

By 1978, Kernighan and Ritchie's book The C Programming Language gave the growing number of C programmers a shared, informal description of the language. It is still nicknamed "K&R" today, after its authors' initials. Its first example program, a few lines that print the words "hello, world," became the traditional first program every C learner writes — including you, in a later chapter.

The book's influence still shows up in code today in a way you will notice without anyone pointing it out: the exact way it lines up opening and closing braces ({ and }) around a block of code became known as "K&R style," and it is still one of the most common brace styles C programmers use. You will see it throughout this course's own example code.

K&R is still worth reading later in your C career, but it was written for programmers who already knew another language, and it explains ideas in a few dense sentences where this course spends a whole chapter. That is a deliberate difference, not an accident: K&R assumed its reader had already climbed the hill you are climbing right now. This course is written for the climb itself.

#include <stdio.h>

int main(void) {
    printf("hello, world\n");
    return 0;
}

You are not compiling this yet — that starts in chapter 0.4, once your machine is set up. For now, notice how old this exact greeting is. People have been typing some version of it since the early 1970s.

K&R's original prints hello, world in lowercase, with a comma. Many tutorials since have printed Hello, World! instead, capitalized, with an exclamation point. Neither is more correct — the words carry no special meaning to the compiler, so the capitalization is only ever a matter of style.

The people behind the language

Ken Thompson and Dennis Ritchie did not stop with C and Unix. In 1983, they jointly received the Turing Award — computing's highest honor, often described as the field's equivalent of a Nobel Prize — for their work on operating system theory and for building Unix itself. Ritchie stayed at Bell Labs for most of his career, later working on successor research operating systems built on what Unix and C had started. Thompson went on, decades later, to co-create another programming language, Go, at Google — a language with its own answer to some of the same problems C first ran into in the 1970s. Neither man set out to build something that would still be running the world's phones and servers fifty years on. They were solving one specific, immediate problem: getting an operating system to run on a computer it was not written for.

Where C is used today

C spreading through universities and companies in the 1970s and 1980s is not only old history — it is the reason C is still everywhere more than fifty years later. Newer languages have replaced C for a great deal of everyday software, especially the kind of program that mainly waits on a person clicking things and does not need every last bit of speed. C did not lose ground there because it stopped working. It lost ground because those newer languages trade away some of C's speed and control for guardrails that make common mistakes harder to make — a fair trade for a lot of software, but not for everything. Three places where that trade still is not worth making are worth naming, since you likely touch all three without noticing.

First, kernels — the core part of an operating system that talks directly to a computer's hardware, the same job Unix's core did in 1973 — are still commonly written in C. The Linux kernel, which runs most of the world's web servers and is the base of Android phones, is written mostly in C, in the same tradition Unix started. Second, embedded systems — small computers built into another device, like a car, a thermostat, or a coffee maker, rather than sold as a computer on their own — very often run C, because C can run fast on hardware too small and low-power for a heavier language. Some of these devices are safety-critical — a car's engine control unit or a hospital ventilator, for example — and the C code inside them often follows an extra, stricter rulebook on top of the standard, called MISRA C, that bans a number of otherwise-legal C patterns known to cause hard-to-find bugs. Third, many programming languages you might learn after this one are not implemented in themselves — their own interpreter or compiler, the program that actually runs your code in that language, is written in C. Python's most widely used implementation, CPython, is one well-known example.

That last point connects directly to this course. Foundations of Programming: C is the first in a small series — the same course also covers C++, once you finish here, and Rust after that. C++ was built as an extension of C itself, adding features on top of everything you are about to learn without taking any of it away. Rust is much newer, designed partly to keep C's speed and closeness to the hardware while catching a category of mistakes at compile time that C leaves entirely up to the programmer — mistakes you will meet firsthand once this course reaches Modules 7 and 8, on dynamic memory. Learning C first, the way this course does, is not an old-fashioned detour before the "real" languages. It is the shared foundation both of those languages were built on top of.

Module 0 has no code exercises yet — those start in Module 1. Instead, try this:

  • Name three pieces of software you use every day. Then guess: could any of them be written in C? (A good bet: anything that runs on Linux, most phone operating systems, and many programming languages themselves are built on C.)
  • Read Dennis Ritchie's own short account of building C, linked below. Look for the part where he describes B's limits — it is the same problem this chapter already described, in the words of the person who solved it.
  • Pick one device in your house that is not a computer, phone, or tablet — a microwave, a car, a thermostat. Guess whether it has a small computer inside it, and what kind of code might run there. (Most modern versions of these do, and C is one of the most common languages for exactly this kind of small, low-power device.)

Zooming out: from why C spread to how the language itself changed

C spread because it solved a real problem: it let an operating system move between computers without a full rewrite. That same trade-off — close to the hardware, but not glued to one machine — is why C is still under so much of the software you use every day, more than fifty years later: the kernel your phone or laptop runs on, the small computer inside a car or a thermostat, and often the very language you might reach for after this one, if that language's own interpreter happens to be written in C.

Notice the shape of this whole story: a real, specific limit (assembly could not move between machines) forced a real, specific fix (a language with real data types, close enough to the hardware to replace assembly without giving up speed). Almost everything else in C's history follows from that one design goal. The book that documented it in 1978, the universities that taught it, the companies that shipped C compilers on their own hardware in the 1980s, even the safety rulebook that now governs C in cars and medical devices — all of it traces back to two programmers who wanted their operating system to run on more than one machine.

C did not stay frozen once it spread, though. The 1978 book that taught a generation of programmers described the language as Kernighan and Ritchie's one compiler understood it — not as a rulebook every compiler maker had agreed to. That gap eventually caused real problems of its own. The next chapter walks through how C changed over time — the versions named C89, C99, C11, C17, and C23 — and explains why this course teaches you C17, the second-newest version, instead of C23, the newest one.
