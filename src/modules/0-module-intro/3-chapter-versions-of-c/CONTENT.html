The Versions of C

Last chapter you learned where C came from, what problem it solved, and why Unix made it spread. Once a language spreads to many computers made by many companies, someone has to write down the exact rules for it, or every computer starts speaking its own private dialect. This chapter is the story of those rulebooks.

Big picture: why C needed an official rulebook

In the early days, "C" meant whatever one particular compiler accepted. A program that worked on one machine could fail on another, for no reason a beginner could see. So a group of engineers wrote down an official rulebook: the exact grammar, the exact behavior, the exact edge cases. Every compiler maker agreed to follow it. That rulebook is called a standard, and C has had five of them. Knowing which one you are writing against tells you which features you can use and which ones will break on someone else's machine.

You will not spend this course debating standards — this chapter exists so that when you see a -std= flag, a warning that mentions "C99" or "C11", or an old tutorial that looks slightly different from what this course teaches, none of it is mysterious. A program is not "C" in some vague, single sense; it is written against one specific, named rulebook, the same way a form is filled out according to one specific year's tax rules. Which rulebook is in play changes what is and is not allowed — everything else about the language stays exactly as familiar as it already is.

A C standard is a rulebook that every compiler maker agrees to follow, and C has been rewritten five times — C89, C99, C11, C17, and C23 — each version adding or clarifying rules on top of the last.

How it works

A standard is a written document, agreed on by a committee, that says exactly what a correct C compiler must do. It is not software — it is a set of rules that software follows. When people say "C99" or "C17", they mean "the version of the rulebook published in that year." Here is the quick version, then each rulebook gets its own closer look below.

StandardYearWhat it changed
C89 (also called ANSI C or C90) 1989 The first official rulebook. Before this, every compiler had its own rules. C89 is the reason old C code from the 1990s still compiles today.
C99 1999 Let you declare a variable anywhere in your code, not only at the top of a block. Added // comments and fixed-width integer types like int32_t, so a number takes up exactly the space you expect on every machine.
C11 2011 Added optional support for threads (code that runs more than one task at once) and atomics (safe ways for those tasks to share data). Both were made optional, which matters later in this course.
C17 2018 Fixed mistakes and unclear wording left over from C11. It added no new features at all — it only clarified the existing rules. This is the rulebook this course uses.
C23 (ISO/IEC 9899:2024) 2024 The current rulebook. Added conveniences like a real true and false built into the language, and nullptr for empty pointers. It is the newest, but the newest rulebook is not always the one every compiler follows yet.

C89: taming a thousand private dialects

Before 1989, the closest thing C had to a rulebook was The C Programming Language, the book by Kernighan and Ritchie you met last chapter. It was clear and well written, but it was a description of one implementation, not a legal contract every compiler maker had to follow. It also left real gaps on purpose, trusting compiler makers to fill them in sensibly. They did not always fill them in the same way.

Two different compilers could disagree on small, sharp-edged questions: how large is an int on this machine? What happens if a number is too big to fit in the space given to it? Can a function be called before its full definition appears in the file? A program that leaned on one compiler's answer to any of these could fail to compile, or worse, compile and behave differently, on another compiler entirely.

In 1983, the American National Standards Institute (ANSI) formed a committee to write an official answer to every one of those questions. It published its rulebook in 1989 — hence "C89." The International Organization for Standardization (ISO) adopted an almost identical version the following year, sometimes called C90. In everyday conversation, "ANSI C," "C89," and "C90" all point at the same rulebook.

"ANSI C" sounds like it should mean "old, out-of-date C." It does not. It means specifically the 1989 standard — the first one. Every standard since, including C23, is still "ANSI C" in the sense that ANSI and ISO keep co-publishing each revision. When someone says "ANSI C" today, they almost always mean C89 by contrast with something newer, not "C in general."

C99: what actually changed for a working programmer

Ten years is a long time for a language to sit still, and by 1999 programmers had a long list of small frustrations. C99 is the rulebook that answered them. Three changes from that list are still the ones you will notice first.

First, C89 required every variable in a block to be declared at the very top, before any other statement — even if you would not use that variable until fifty lines later. C99 dropped that rule. You can now declare a variable exactly where you first need it, including inside the parentheses of a for loop:

/* legal in C89 — declaration must come first */
int i;
for (i = 0; i < 10; i++) { /* ... */ }

/* legal only from C99 onward — declared right where it's used */
for (int i = 0; i < 10; i++) { /* ... */ }

Second, C99 added // for a comment that runs to the end of the line. C89 only had /* ... */, which needs an opening and a closing mark and reads awkwardly for a quick one-line note. Both styles work in every standard this course covers, but you will see // far more often in code written after 1999.

Third, C99 added fixed-width integer types — whole-number types, declared in <stdint.h>, that name their exact size instead of leaving it up to the compiler. Plain int is at least 16 bits, but a compiler is free to make it bigger, and different machines have made different choices over the decades. int32_t is always exactly 32 bits, everywhere, on every machine that supports it. When a number's size genuinely matters — reading a file format that another program wrote, for instance — a fixed-width type removes the guesswork.

None of this is retroactive. A compiler that only understands C89 will refuse to compile a for (int i = 0; ...) loop or a // comment — not because the code is wrong, but because that compiler's rulebook has no entry for it yet. This is exactly why the -std= flag you will meet later in this chapter exists: it tells the compiler which rulebook's entries to look up.

C11: features a compiler is allowed to skip

C11 introduced something the earlier standards had not needed: an optional feature, a piece of the standard a compiler is allowed to leave out entirely and still legitimately claim "I support C11." Threads (<threads.h>, for running more than one task at once) and atomics (<stdatomic.h>, for letting those tasks share data safely) were both made optional this way.

Why would a standard allow a compiler to skip part of itself? Because by 2011, C already ran on operating systems with wildly different native ways of handling threads, and forcing every compiler maker to build a matching one from scratch would have kept many of them from ever reaching C11 conformance at all. Making threads optional let compiler makers catch up to the rest of C11 immediately and add thread support on their own timeline — or never, if their platform already had a preferred way to do it.

This is not a hypothetical corner case for this course. Apple's Clang compiler, which this course's setup chapter has many of you installing, does not ship <threads.h> at all — trying to #include it fails with file not found. That is a legal, standard-conforming choice by Apple, not a bug. It is also exactly why this course teaches thread programming with the older, universally available pthreads library in Module 12, and covers <threads.h> afterward, in Module 13, as a comparison — you will have a working, portable skill before you meet the one that might not even compile on your machine.

C17: a rulebook with no new rules

C17 is the odd one out in this table: it added nothing. Between 2011 and 2017, people actually using C11 in real projects found spots where the wording was ambiguous, or where two parts of the document quietly contradicted each other. C17's entire job was to fix those spots — a pass of corrections and clearer wording, with zero new features. Programmers sometimes call this kind of release a technical corrigendum, which is a formal way of saying "we fixed typos and contradictions, we did not change what the language does."

A rulebook with no new features can still matter. Ambiguous wording is not a cosmetic problem — two compiler makers reading the same unclear sentence in C11 could each build a "correct" compiler that disagreed with the other on some edge case, and a program that happened to depend on one compiler's interpretation could compile differently, or not at all, on the other. C17 closed exactly those gaps, which is part of why it is a dependable target for a course that has to behave the same way on Windows, macOS, and Linux at once.

C23: the newest rulebook, not yet the safest bet

C23, officially ISO/IEC 9899:2024, is the current standard as of this writing. It adds real conveniences: true, false, and bool are now built-in keywords — words the language reserves for its own use — instead of macros you had to #include <stdbool.h> to get. nullptr gives pointers a dedicated "points at nothing" value, distinct from the number 0. C23 even added a way to write whole numbers in binary directly in your source code, like 0b101 for the number five, without any library trick to make it work.

None of that makes C23 the right target for this course yet, for the same reason C17 is: a standard is only as useful as the compilers that fully implement it, and as of this writing, Apple's Clang supports C23 only partially. A beginner has no reliable way to tell, feature by feature, which parts of C23 will compile on their own machine and which will not — and a course that breaks on some learners' laptops and not others is a broken course. C17 is completely and predictably supported everywhere this course runs.

"Newest" and "best choice for right now" are not the same question. A standard can be finished, official, and still not be the one you should compile against today — that depends on whether the tools you actually have catch up to it. This is worth remembering well past this course: professional C teams often stay one or two standards behind the newest release, for exactly this reason.

The number in the name

The formal name for a C standard is not "C17" — it is something like ISO/IEC 9899:2018. 9899 is a fixed document number ISO assigned to the C standard once, permanently; it never changes between revisions. The number after the colon is the year ISO officially published that revision. So "C17" (informal, based on when the committee finished its work) and "ISO/IEC 9899:2018" (formal, based on when ISO's publishing process completed) name the exact same document — you will see both "C17" and "C18" used for it in the wild for precisely this reason, and neither is wrong.

You do not need to memorize any of these formal names. This course will only ever say "C17." But if you ever go looking at cppreference or an official standards page and see "9899:2018" where you expected "C17," you now know why: same rulebook, two different ways of dating it.

If a search for "C18" turns up nothing useful, try "C17" instead, and the other way around — many pages, tools, and even compiler flags pick one name and stick with it. GCC and Clang's own -std=c17 and -std=c18 flags are accepted as exact synonyms for this reason, and either one compiles your code identically.

Who actually writes a standard?

No single company owns C, which is part of why a rulebook is necessary in the first place. The actual writing is done by a group called WG14 — short for "Working Group 14" — a committee under ISO, the same international body that standardizes things like paper sizes and shipping container dimensions. WG14's members are not one company's employees; they come from compiler makers, hardware companies, universities, and independent C experts around the world, each representing their own country's national standards body.

Turning an idea into part of the standard takes years, not weeks. Someone writes a formal proposal explaining exactly what should change and why. WG14 discusses it, revises the wording, and eventually folds accepted proposals into a public draft. That draft goes out for review — genuinely public, published for anyone to read and comment on — before a final vote. A brand-new feature proposed today realistically will not appear in a shipping compiler for several years, which is one more reason this course does not chase the newest standard the moment it is announced.

Nobody can single-handedly add a feature to C, not even a huge company. A compiler maker can add its own private extension — a feature that only works on that one compiler — but that is not the same as it becoming part of the standard, and code that relies on it will not compile anywhere else. This course never teaches compiler-specific extensions, only what every C17 compiler is guaranteed to support.

Why not one perfect version?

A reasonable question: if C89 had problems, why not fix them completely and be done, instead of publishing four more rulebooks over the following decades? The answer is a tension every long-lived standard has to manage: millions of lines of C code already existed by the time each new standard was being written, and almost none of it could be rewritten only because the rulebook changed underneath it.

Think of it like a city adding new traffic laws. A city can require every new intersection to have a left-turn signal. What it cannot reasonably do is make every existing intersection illegal overnight and force every driver to relearn the road from scratch. New rules layer on top of old ones; the old ones keep working. That is exactly the promise the Zoom Out section below names: every C standard since C89 has been additive. C99 did not remove anything C89 allowed. C23 does not remove anything C17 allowed. A feature can be added; a working feature is essentially never taken away, because doing so would break code nobody at WG14 has even seen.

The analogy is not perfect — a city's roads are physical and a codebase is text, so a codebase actually could be rewritten given enough time and money. The real-world reason it usually is not comes down to cost and risk: rewriting millions of working, tested lines on the hope of a cleaner rulebook risks introducing new bugs to fix an inconvenience, not a defect. Staying additive is what makes upgrading a compiler a safe, boring event instead of a project of its own.

Telling standards apart by their features

You do not need to memorize five dates. In practice, you can often tell which standard a piece of code was written against by which features show up in it — a kind of fingerprint left behind by the rulebook the author was using.

You see this in the code……it needs at least
A variable declared inside a for (...)C99
A // commentC99
int32_t, uint8_t, or another <stdint.h> typeC99
_Atomic or <stdatomic.h>C11
<threads.h>C11 (and only where a compiler chose to implement it)
true/false with no #include <stdbool.h> anywhereC23
nullptrC23

Try it on a real snippet. Here is a small function with no comments telling you anything about which standard it targets:

int32_t sum_first_n(int32_t n) {
    int32_t total = 0;
    for (int32_t i = 0; i < n; i++) {
        total += i;
    }
    return total;
}

Two clues place this squarely in C99 or later. int32_t is a fixed-width type from <stdint.h> — not available before C99. And i is declared inside the for (...) parentheses, the declare-anywhere feature from earlier in this chapter. Neither clue on its own would be certain proof — a project could define its own type also named int32_t, for instance — but together, two independent fingerprints pointing the same direction is good evidence. Nothing here needs C11 or C23 at all, so on the evidence alone this snippet could target anything from C99 up through C23.

The most direct source of truth is not a feature at all — it is the exact -std= flag a project's own build instructions use, when they say. A project's README, Makefile, or build script will often name it outright, which is more reliable than guessing from features alone: a codebase can compile against C17 while never happening to use any feature newer than C89.

Does this matter for you yet?

Not much, and that is by design. Every program you compile in this course uses the exact same -std=c17 flag, so you will never hit a mismatch between what you wrote and what your compiler expects — that entire category of problem is handled for you before you start typing. Where this chapter's knowledge pays off is later, outside this course: the day you open somebody else's project, or a library's documentation, and see a feature you do not recognize. Instead of being stuck, you will know to ask one question — which standard is this written against? — and the table above will usually answer it.

Here is what that moment actually looks like. Say you download an open-source C project to see how it works, and its README says nothing about which standard it targets. You open its Makefile and find a line like CFLAGS = -std=gnu11 -Wall. Two things to notice: -std=gnu11 is not one of the five standards in this chapter's table — it is GCC's own "C11 plus a handful of GCC-specific extras" flavor, which is why compiler-specific flags exist alongside the plain -std=c11 this chapter has been teaching. And now you know something useful before reading a single line of that project's code: it expects at least C11, so a fixed-width type or an _Atomic variable appearing later will not be a surprise. That is the entire payoff of this chapter — not memorizing five years, but knowing where to look and what the answer tells you.

You tell a compiler which rulebook to use with a flag on the command line. This course always compiles with:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello

-std=c17 tells the compiler: "follow the C17 rulebook, and nothing newer." You will type this exact flag on every program you compile in this course.

C23 is the current standard, so why does this course pin C17 instead? Because this course has to run the same way on every learner's computer — Windows, Linux, and macOS — with no setup beyond installing a compiler. Apple's own compiler (Clang, which ships with every Mac) only partially supports C23 as of this writing: some C23 features work, some do not, and a beginner has no way to tell which is which. C17 is fully and reliably supported everywhere this course runs. When your whole toolchain supports C23 completely, you can switch the flag to -std=c23 and everything you learned still applies — a later standard never removes what an earlier one taught you.

Zooming out: from picking a rulebook to installing the tools that enforce it

Every standard after C89 has been additive: newer rulebooks add or clarify, they do not take away. That is why code written for C17 still makes sense once you know C23 exists, and it is why this course can teach you real, useful C on the C17 rulebook without shortchanging you. Everything you practice against C17 keeps working the day you eventually move to a newer standard — nothing here is a detour you will later have to unlearn. Next chapter you install a compiler, use it to enforce that -std=c17 flag yourself, and compile and run your first program.
