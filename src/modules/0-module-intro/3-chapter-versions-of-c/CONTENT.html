The Versions of C

Last chapter you learned where C came from, what problem it solved, and why Unix made it spread. Once a language spreads to many computers made by many companies, someone has to write down the exact rules for it, or every computer starts speaking its own private dialect. This chapter is the story of those rulebooks.

Big picture: why C needed an official rulebook

In the early days, "C" meant whatever one particular compiler accepted. A program that worked on one machine could fail on another, for no reason a beginner could see. So a group of engineers wrote down an official rulebook: the exact grammar, the exact behavior, the exact edge cases. Every compiler maker agreed to follow it. That rulebook is called a standard, and C has had five of them. Knowing which one you are writing against tells you which features you can use and which ones will break on someone else's machine.

A C standard is a rulebook that every compiler maker agrees to follow, and C has been rewritten five times — C89, C99, C11, C17, and C23 — each version adding or clarifying rules on top of the last.

How it works

A standard is a written document, agreed on by a committee, that says exactly what a correct C compiler must do. It is not software — it is a set of rules that software follows. When people say "C99" or "C17", they mean "the version of the rulebook published in that year."

StandardYearWhat it changed
C89 (also called ANSI C or C90) 1989 The first official rulebook. Before this, every compiler had its own rules. C89 is the reason old C code from the 1990s still compiles today.
C99 1999 Let you declare a variable anywhere in your code, not only at the top of a block. Added // comments and fixed-width integer types like int32_t, so a number takes up exactly the space you expect on every machine.
C11 2011 Added optional support for threads (code that runs more than one task at once) and atomics (safe ways for those tasks to share data). Both were made optional, which matters later in this course.
C17 2018 Fixed mistakes and unclear wording left over from C11. It added no new features at all — it only clarified the existing rules. This is the rulebook this course uses.
C23 (ISO/IEC 9899:2024) 2024 The current rulebook. Added conveniences like a real true and false built into the language, and nullptr for empty pointers. It is the newest, but the newest rulebook is not always the one every compiler follows yet.

You tell a compiler which rulebook to use with a flag on the command line. This course always compiles with:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello

-std=c17 tells the compiler: "follow the C17 rulebook, and nothing newer." You will type this exact flag on every program you compile in this course.

C23 is the current standard, so why does this course pin C17 instead? Because this course has to run the same way on every learner's computer — Windows, Linux, and macOS — with no setup beyond installing a compiler. Apple's own compiler (Clang, which ships with every Mac) only partially supports C23 as of this writing: some C23 features work, some do not, and a beginner has no way to tell which is which. C17 is fully and reliably supported everywhere this course runs. When your whole toolchain supports C23 completely, you can switch the flag to -std=c23 and everything you learned still applies — a later standard never removes what an earlier one taught you.

Zooming out: from picking a rulebook to installing the tools that enforce it

Every standard after C89 has been additive: newer rulebooks add or clarify, they do not take away. That is why code written for C17 still makes sense once you know C23 exists, and it is why this course can teach you real, useful C on the C17 rulebook without shortchanging you. Next chapter you install a compiler, use it to enforce that -std=c17 flag yourself, and compile and run your first program.
