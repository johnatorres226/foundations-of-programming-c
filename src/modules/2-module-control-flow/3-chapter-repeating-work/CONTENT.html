Last chapter you combined conditions with &&, ||, and !, and learned why short-circuit evaluation matters for safety — a left-hand check that fails can stop an unsafe right-hand check from ever running. This chapter reuses that same idea, a condition that is either true or false, for a new job: not deciding whether to run a block of code once, but deciding how many times to run it, and how to be sure it eventually stops.

Big picture: why C gives you three different ways to repeat something

Every program you have written so far runs each line exactly once, top to bottom. That is fine for a program that prints one message or checks one condition. It falls apart the moment a task is naturally repetitive: add up a hundred numbers, print every row of a table, keep asking a person for input until they type something valid. Typing the same line a hundred times is not a real option. A loop is C's answer: a block of code you write once that the computer runs over and over, as many times as a condition says it should.

Each single run of a loop's body is called an iteration. What changes between one loop and the next is not whether it repeats — every loop does that — but two much more specific questions: does the body need to run at least once no matter what, and do you already know how many iterations you need before the loop starts? C gives you three loop forms — while, do/while, and for — because those two questions have different honest answers depending on the task, and forcing every task through one shape of loop hides which answer actually applies.

This is not C being generous with syntax for no reason. Every one of these three forms compiles down to the same handful of machine instructions: check a condition, maybe jump backward, maybe jump forward past the loop. Choosing between them is a readability decision, not a performance one — the right choice tells the next person reading your code (often you, in a week) what kind of repetition this is, before they read a single line of the body. A for loop announces "this runs a known number of times." A while loop announces "this keeps going as long as something stays true, and might not run at all." A do/while loop announces "this always runs at least once." Picking the wrong one does not just look worse — it hides the real shape of what your program does from anyone reading it, including future you.

The harder problem sits underneath all three: a loop that never stops is not a slower program, it is a broken one. Chapter 1.5 showed you a program can compile clean under -Werror and still be wrong at runtime. A loop is the clearest place that happens — the compiler cannot tell you whether your condition will ever become false, only you can reason that out. This chapter's real subject, underneath the three keywords, is that reasoning: how to look at a loop and know, before you run it, that it will actually end.

A recipe makes the same three-way distinction, without ever naming it. "Stir until the batter is smooth" is a while: you do not know in advance how many stirs that takes, and if the batter came out of the bag already smooth, you would not stir at all. "Add the eggs, then taste it and adjust" is a do/while: tasting always happens at least once, adjusting is optional after that. "Stir 20 times" is a for: a fixed count, known before you start, with nothing in the recipe that depends on what the batter actually looks like. None of the three instructions is wrong on its own — a recipe writer picks whichever one actually describes when to stop, and so do you, every time you write a loop.

A loop repeats a block of code while a condition holds true, and C's three loop forms — while, do/while, and for — exist to match how a task's iteration count and start-up condition actually behave.

How it works

The while loop

A while loop checks a condition — an expression C treats as true or false, the same kind you used with if — before every iteration. If the condition is false the very first time, the body never runs at all: zero iterations is a completely normal outcome for a while loop, not an edge case to work around.

The code between a loop's { } is its loop body — the part that actually repeats. Everything outside those braces, the condition and whatever comes after the loop, runs on its own schedule: the condition once per iteration, the code after the loop exactly once, the moment the condition finally turns false.

#include <stdio.h>

int main(void) {
    int n = 5;

    while (n > 0) {
        printf("%d\n", n);
        n--;
    }
    printf("Liftoff!\n");
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror countdown.c -o countdown
$ ./countdown
5
4
3
2
1
Liftoff!

Read this the way the computer does. Check n > 0. It is true (n is 5), so run the body: print 5, then subtract one from n. Go back to the top. Check again. Keep doing this until n reaches 0, at which point n > 0 is false, the loop ends, and control falls through to printf("Liftoff!\n"). Nothing here is special syntax — it is the same kind of condition you have already written in an if, checked over and over instead of once.

C's if and loops all attach to exactly one statement unless you wrap the body in { }. while (n > 0) printf("%d\n", n); n--; (no braces) only repeats the printf — the n--; is a separate statement that runs once, after the loop, not part of it. Since n never changes inside the actual loop body, that version never terminates. Always use { } around a loop body with more than one statement, and most style guides say to use it even for one statement, since adding a second line later is an easy way to reintroduce this exact bug.

Of the three loop forms this chapter covers, while is the most basic one — the other two are really while wearing different clothes. do/while is a while loop with its first condition check skipped. for is a while loop with its setup and update lines folded onto one line instead of scattered across three. Anything you can write with for or do/while, you could also write with a plain while — the other two forms exist purely to say, in the shape of the code itself, which specific pattern of repetition you mean.

The do/while loop

A do/while loop flips the order: it runs the body first, and checks the condition afterward, at the bottom. That means the body always runs at least once, even if the condition was already false before the loop started. This is the one situation a plain while cannot express directly — with while, a false condition on the first check skips the body entirely, no exceptions.

#include <stdio.h>

int main(void) {
    int n = 0;

    do {
        printf("n is %d\n", n);
        n++;
    } while (n < 0);

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror do_while_demo.c -o do_while_demo
$ ./do_while_demo
n is 0

Notice the condition, n < 0, is false from the very first check — n is 0, not negative. A while (n < 0) { ... } written the same way would print nothing at all, since it checks before running anything. The do/while version still prints n is 0 exactly once, because it always runs the body before it ever looks at the condition. Reach for do/while specifically when a task must happen at least once by definition — no reasonable version of the task can run zero times — and only afterward decides whether to repeat.

do/while is the one loop that needs a semicolon after its condition: do { ... } while (n < 0);. Forget it, and most compilers report a confusing error pointing at the next line, not the missing semicolon itself, since the parser was still expecting one when it read further. If a do/while loop won't compile and the error looks like it is about something unrelated below it, check the semicolon first.

do/while is the least common of the three loop forms in real C code, precisely because "must run at least once" is a narrower situation than it first sounds. The classic case is asking a person for input and re-asking only if what they typed was invalid — you cannot check whether their answer was valid before they have given one, so the asking has to happen first, and the checking second. A later chapter puts real input reading into that pattern; for now, notice the shape: do { get an answer; } while (the answer was not good enough);. Whenever you catch yourself writing a while loop and then also writing a copy of its body just above it so the first check has something to look at, that duplication is usually a sign the task actually wanted do/while all along.

The for loop

A for loop is a while loop with its three moving parts gathered into one line: where the loop variable starts, what condition keeps it going, and how it changes after each iteration.

#include <stdio.h>

int main(void) {
    for (int i = 1; i <= 5; i++) {
        printf("%d x 3 = %d\n", i, i * 3);
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror times_table.c -o times_table
$ ./times_table
1 x 3 = 3
2 x 3 = 6
3 x 3 = 9
4 x 3 = 12
5 x 3 = 15

The three parts inside for ( ; ; ) run in a fixed order, and it is worth naming each one exactly once: int i = 1 is the initializer, and it runs exactly once, before the loop starts anything. i <= 5 is the condition, checked before every iteration, the same as a while. i++ is the update, and it runs after the body, at the end of every iteration — not before, and not instead of the body. Writing this same loop with while takes three separate lines instead of one:

int i = 1;
while (i <= 5) {
    printf("%d x 3 = %d\n", i, i * 3);
    i++;
}

Both versions do exactly the same thing. The for version is preferred whenever you already know, before the loop starts, roughly how many times it needs to run and what is counting up (or down) to get there — a fixed range, a count, a table. Gathering the start, the check, and the update onto one line means all three are sitting next to each other, so a reader (and you, checking your own work) can see the whole shape of the repetition at a glance, instead of hunting for the update somewhere inside the body.

A loop condition is a comparison, written with <, <=, or ==. Typing a single = instead — an assignment — is valid C, so the compiler will not stop you: for (int i = 0; i = 5; i++) assigns 5 to i every single iteration, and 5 is treated as true (any nonzero number is), so the condition never becomes false. This is one of the most common ways beginners accidentally write an infinite loop, and it is worth reading your own loop conditions back once, slowly, checking for a lone = where you meant ==.

A variable declared inside the for's own parentheses, like i above, only exists inside that loop — the moment the loop ends, C forgets i entirely, and trying to use it in a printf after the closing } is a compile error, not a leftover value. This mirrors Chapter 1.3's rule about a variable declared inside main's braces: where you declare something decides how long it lives. It also means two different for loops in the same function can both use i as their counter without conflict, since each loop's i belongs only to that loop. You can also leave any of the three parts empty — for (;;) { ... } is a loop with no built-in condition at all, which runs forever unless something inside the body itself decides to stop it. Next chapter's break is exactly how a loop body makes that decision.

Off-by-one: getting the boundary right

An off-by-one error is a loop that runs one time too many, or one time too few, because its condition drew the boundary in the wrong place. It is called that because the bug is never "the loop is completely wrong" — it is almost right, out by exactly one iteration, which is exactly what makes it easy to miss.

#include <stdio.h>

int main(void) {
    /* Meant to print 1 through 5. */
    for (int i = 1; i < 5; i++) {
        printf("%d\n", i);
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror off_by_one.c -o off_by_one
$ ./off_by_one
1
2
3
4

5 never prints. The condition i < 5 is false the moment i reaches 5, so the loop stops one iteration short of what "1 through 5" actually means. The fix is i <= 5 — include the endpoint, not stop before it. There is no shortcut that avoids this trap other than checking, for every loop you write, exactly which numbers it is supposed to touch and reading your condition back against that: does it include the first one, and does it include the last one?

This chapter's fourth exercise, counting multiples of a step up to a limit, is built around exactly this boundary. When the limit itself is one of the multiples (like 9 being a multiple of 3), the condition has to accept it, not stop one short of it.

The same boundary question shows up the other direction, too, once counting starts from 0 instead of 1 — which is exactly how Module 4's arrays count. A list of 5 items is numbered 0, 1, 2, 3, 4 — five positions, but the last one is 4, not 5. A loop meant to touch every item, written for (int i = 0; i <= 5; i++), runs one time too many instead of too few, reaching for a sixth position that was never part of the list. "How many items" and "what is the last valid position" are off by one from each other whenever counting starts at 0, and mixing the two up is the single most common off-by-one mistake once arrays enter the picture.

Loops that don't stop: reasoning about termination

An infinite loop is a loop whose condition never becomes false, so it never stops on its own. The program does not crash — it just keeps running, forever, doing whatever the body does, until something outside the program (you, pressing Ctrl-C, or the operating system running out of patience) kills it. This is the failure mode Chapter 1.5 warned you about: a program that compiles clean and starts up fine, but is still wrong.

/* BROKEN — do not run this. n never changes, so n > 0 is always true. */
int n = 5;
while (n > 0) {
    printf("%d\n", n);
}

Compare that to the working countdown from the start of this chapter. The only difference is one missing line, n--;. Without it, n is 5 forever, n > 0 is true forever, and the loop prints 5 forever. If you ever run a program and it seems to hang — no output, no prompt back, nothing — a loop that forgot to update its own condition is the first thing to suspect. Ctrl-C, the interrupt key Chapter 1.5 introduced for stopping a stuck program, is exactly the tool for getting your terminal back when this happens.

The way to be sure a loop terminates, before you ever run it, is to find one quantity in the condition that moves, every single iteration, toward the value that makes the condition false — and to check it actually can get there. In the countdown, that quantity is n: it strictly decreases by exactly 1 each time, and it starts at a normal, finite number, so it is guaranteed to reach 0 eventually. In the times-table for loop, i strictly increases toward 5. This chapter's fifth exercise asks you to reason about a loop the other direction — a value that doubles every iteration — and to see why doubling toward a target is just as guaranteed to arrive as counting down by ones, even though it gets there in fewer steps.

"It decreases" is not automatically enough — it has to decrease toward something the condition actually stops at. A loop counting down an unsigned int with while (n >= 0) never stops: an unsigned type cannot go below 0, so when n reaches 0 and the loop subtracts one more, it wraps around to a huge positive number instead of becoming negative — the exact wraparound Chapter 1.3 covered — and n >= 0 stays true forever. The quantity has to reach the condition's actual stopping point, not just head in a promising direction.

A staircase makes the reasoning concrete without any code at all. Someone climbing a staircase to a specific floor is guaranteed to arrive eventually, as long as every step actually moves them one step closer, and the staircase has a finite number of steps. If a "step" ever failed to move them closer — if they stepped in place, or the staircase turned out to have no top floor — climbing would never finish, no matter how much climbing happened. That is the entire test for whether a loop terminates: does every iteration genuinely move the loop variable one step closer to the condition's stopping point, and is the distance to travel finite? Not every loop you write later in this course can be checked this cleanly — a loop that searches a list for a value that might not be in it needs a second way out, which is exactly what break is for, next chapter — but the countdown, doubling, and boundary examples in this chapter all pass the staircase test directly.

Zooming out: from repeating one thing to choosing among many

You can now choose the right loop for a task — while when zero iterations is a real possibility, do/while when the body must run at least once by definition, for when you already know roughly how many iterations you need — and, just as importantly, you can look at a loop you did not write and check whether it actually terminates: find the quantity that moves toward the stopping condition every iteration, and confirm it can really get there.

Every loop in this chapter picked one specific job and repeated it, the same job, every single iteration. Real programs often need to do something slightly different depending on which iteration it is, or on some other condition checked partway through the loop's own body — skip this one, stop early once you find what you were looking for, react differently to a handful of specific cases. Next chapter, Choosing Many Paths, covers switch, C's tool for picking one path out of several based on a single value, and explains fall-through — what happens between two switch cases if you forget to say otherwise. It also names two keywords this chapter deliberately left alone, break and continue: both jump out of a loop's normal flow early, and next chapter is where you learn to reach for each of them on purpose, not by accident.

Every module ahead assumes you can read a loop and immediately answer three questions: what is it repeating, why did the author pick this loop form over the other two, and will it actually stop. Arrays and strings, starting in Module 4, are walked almost entirely with for loops — a loop over every element of a fixed-size list is the single most common loop shape in the rest of this course, and it is built from exactly the three parts you just learned to read at a glance. Loops inside functions, Module 3's subject, work no differently than the loops in this chapter's main — a loop does not care whether it is sitting in main or in a function you wrote yourself, only that its body and condition are still correct wherever it lives.

One shape you have not seen yet is a loop inside another loop — a nested loop, where each single iteration of the outer loop runs the entire inner loop from start to finish. Printing a full multiplication table, not just one row like this chapter's example, needs exactly that: an outer loop over each row, and an inner loop, a complete copy of this chapter's for loop, over each column within it. Nothing new to learn there either — it is the same three loop forms, the same termination reasoning, applied twice, once inside the other.
