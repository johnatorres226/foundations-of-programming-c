Homework: Repeating Work

You've read how while, do/while, and for each decide when to check their condition, plus the off-by-one boundary and the infinite loop that catch nearly every beginner at some point. Now put it into practice: five small functions, written from scratch in exercises/ and checked with make check-mine — not by reading this page.

exercises/01_sum_of_digits.c

Write a function int sum_of_digits(int n) that adds up the decimal digits of a non-negative int and returns the total. sum_of_digits(123) should return 6 (1 + 2 + 3), and sum_of_digits(0) should return 0.

The chapter's "The while loop" section showed a while loop that checks its condition before every iteration, and can run zero times. Work out what n % 10 and n / 10 do to a number one digit at a time, and why a while loop — not a do/while — is the right fit for the case n is already 0.

n has to actually shrink somewhere inside your loop body, or the condition never turns false — this is precisely the termination reasoning the chapter's "Loops that don't stop" section walked through.

exercises/02_count_digits.c

Write a function int count_digits(int n) that returns how many decimal digits a non-negative int has. count_digits(123) should return 3. count_digits(0) should return 1 — zero is one digit long, not zero digits long.

The chapter's "The do/while loop" section showed exactly this shape of problem: something that must happen at least once no matter what, checked only afterward. Prove to yourself why a plain while loop gets count_digits(0) wrong, and do/while gets it right.

Don't forget the semicolon after while (...) at the bottom of a do/while loop — it is the one loop form that needs one there, and a missing one often produces a compiler error pointing somewhere else entirely.

exercises/03_sum_range.c

Write a function int sum_range(int lo, int hi) that returns the sum of every whole number from lo to hi, inclusive. Tests only ever call it with lo <= hi. sum_range(1, 5) should return 15; sum_range(5, 5), a range of exactly one number, should return 5.

The chapter's "The for loop" section built a times table with a known, bounded count. Work out how to start a for loop at lo instead of a fixed number like 1, and stop it at hi instead of a fixed number like 5.

sum_range(5, 5) is the case worth checking by hand before you run the tests: does your loop condition let it run exactly once, or does it accidentally skip the single number entirely?

exercises/04_count_multiples.c

Write a function int count_multiples(int limit, int step) that returns how many multiples of step — step, 2 * step, 3 * step, and so on — are less than or equal to limit. Tests only ever call it with limit >= 0 and step >= 1. count_multiples(10, 3) should return 3 (3, 6, 9).

The chapter's "Off-by-one: getting the boundary right" section is built entirely around this exercise's trap. Figure out what count_multiples(9, 3) has to return, and check your loop condition actually agrees with you.

When limit itself is a multiple of step — like 9 and 3 — it has to be counted. A condition that stops one iteration early will quietly undercount by exactly one, the classic off-by-one shape.

Stuck? Show one approach 
int count_multiples(int limit, int step) {
    int count = 0;
    for (int i = step; i <= limit; i += step) {
        count++;
    }
    return count;
}

This is one approach, not the answer. Notice the loop starts i at step, not 0 or 1 — the first multiple of step is step itself.

exercises/05_first_power_of_two_at_least.c

Write a function int first_power_of_two_at_least(int target) that returns the smallest power of two (1, 2, 4, 8, 16, ...) that is greater than or equal to target. first_power_of_two_at_least(5) should return 8; first_power_of_two_at_least(8), where target already is a power of two, should return 8 again, not 16.

The chapter's "Loops that don't stop" section asked you to find the quantity that moves toward a loop's stopping condition every iteration. Work out what that quantity is here, and why doubling it is equally guaranteed to reach target as counting up by ones — only faster.

Start your answer at 1, not 0 — doubling 0 forever never produces anything but 0, which is exactly the "quantity that never moves" trap the chapter's termination section warned about.
