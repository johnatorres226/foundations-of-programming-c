Last chapter you learned to choose correctly between while, do/while, and for, and to write loops that actually stop instead of running forever. This chapter is not about repeating work — it is about picking one path out of several, the way if/else already let you do, but built for a single value that must match one of several exact cases.

Big picture: why C gives you a second way to branch

Module 2 opened with if, else if, and else, and chapter 2.2 added &&, ||, and ! to combine conditions. Between the two, you can already write any branch this course will ever ask you to write. So why does C bother with a second branching tool at all?

Picture a program that reads a single number — a menu choice, a day of the week, a grade letter — and has to do something different for each exact value it might be. Written with if/else if, that looks like this:

if (choice == 1) {
    print_hours();
} else if (choice == 2) {
    print_menu();
} else if (choice == 3) {
    print_directions();
} else if (choice == 4) {
    print_phone_number();
} else {
    printf("Not a valid choice.\n");
}

Nothing here is wrong. It compiles, it runs, and it does exactly what it looks like it does. But read it again and notice what repeats: choice ==, four times, testing the same single variable against four different exact numbers. An if chain is built for conditions that can be anything — a range, a comparison, a combination of several variables. When what you actually have is one variable and a list of exact values it might equal, repeating choice == on every line is the language telling you, quietly, that a more specific tool exists.

That tool is switch. A switch statement names the variable once, then lists the exact values it might match as separate case labels underneath. It reads top to bottom as "when choice is this, do this; when it's that, do that" — the same intent as the if chain above, spoken more directly. Compilers can also often turn a switch with many cases into a single jump straight to the matching case, instead of testing each value one at a time the way an if chain must — though C never promises this, and it is not the reason to reach for switch. The real reason is what the reader sees: one value, a menu of exact matches, laid out so the shape of the decision is visible at a glance.

You will meet this exact shape constantly once you start writing real programs. A calculator program dispatches on which operator character the person typed — '+', '-', '*', '/'. A command-line tool dispatches on which subcommand its first argument named. A game's turn loop dispatches on which menu number a player entered. In every one of these, there is exactly one value, and a fixed, known set of exact things it might be — precisely the situation switch was built for, and precisely the situation where an if chain's repeated choice == starts to feel like the wrong tool doing the right job.

switch is not a replacement for if. It only compares one value against exact constants — it cannot ask "is age greater than 18," the way if can, and it cannot test a float or a piece of text at all, only whole-number types like int, char, and the enumerated types Module 6 introduces. This chapter is about what switch can do inside that narrower job, and about two small keywords — break and continue — that control exactly how far execution travels once it starts down one of these paths.

switch picks one path out of several exact values, and unless you stop it with break, it keeps running into the next one too.

How it works

The switch statement

A switch statement names one expression, then lists case labels — exact constant values that expression might equal. Execution jumps straight to the matching label and keeps running from there, line by line, until it hits a break or reaches the end of the switch. A final, optional default label catches any value that matched nothing above it — the same job else does at the end of an if chain.

#include <stdio.h>

int main(void) {
    int choice = 2;

    switch (choice) {
    case 1:
        printf("Store hours: 9am to 6pm\n");
        break;
    case 2:
        printf("Today's menu: soup and bread\n");
        break;
    case 3:
        printf("We are two blocks north of the station.\n");
        break;
    default:
        printf("Not a valid choice.\n");
        break;
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror switch_basics.c -o switch_basics
$ ./switch_basics
Today's menu: soup and bread

Every case label needs a constant expression — a value the compiler can work out before your program ever runs, like a literal number or a named constant. case choice: or case some_variable: will not compile; only the value being switched on is allowed to be a variable. Two case labels can never share the same value either — the compiler rejects a second case 2: in the same switch as a duplicate, since execution could never know which one you meant.

The value being switched on does not have to be an int. It can be any of C's whole-number types, including char — and a char switch reads especially naturally, since a character literal like 'A' is itself a constant expression:

#include <stdio.h>

int main(void) {
    char grade = 'B';

    switch (grade) {
    case 'A':
        printf("Excellent work.\n");
        break;
    case 'B':
        printf("Good work.\n");
        break;
    case 'C':
        printf("Passing.\n");
        break;
    default:
        printf("Not a recognized grade.\n");
        break;
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror grade_letter.c -o grade_letter
$ ./grade_letter
Good work.

A plain number like 1 or 2 in a case label tells the compiler exactly what it needs, but it tells a human reading the code nothing about why that number matters. Real C code often gives each case a name instead, using either #define (Module 10 covers the preprocessor properly) or an enum — a type built exactly for naming a small, fixed set of whole-number constants, which Module 6 covers in full. Either way, the switch itself does not change at all; only what each case label is called does.

Fall-through is the default

Look again at switch_basics.c above and notice every single case ends with break;. That is not a style choice — leave one out, and execution does not stop at the end of that case's code. It keeps running straight into the next case's code too, matched or not. This behavior has a name: fall-through, and in C it is the default, not something you opt into.

#include <stdio.h>

int main(void) {
    int choice = 1;

    switch (choice) {
    case 1:
        printf("Store hours: 9am to 6pm\n");
        /* no break here! */
    case 2:
        printf("Today's menu: soup and bread\n");
        break;
    default:
        printf("Not a valid choice.\n");
        break;
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror missing_break.c -o missing_break
$ ./missing_break
Store hours: 9am to 6pm
Today's menu: soup and bread

choice is 1, so execution starts at case 1: exactly like before. But with no break at the end of that case, it does not stop there — it falls straight through the case 2: label and keeps running, printing the menu too, before finally reaching a break. The program printed two lines for one choice, and nothing about the code shouted an error. This is the single most common beginner mistake with switch: a missing break that leaves the program quietly doing more than it should, for one specific input, in a way that might not surface until someone tests exactly that case.

Most other languages you might meet later — Python has no switch at all; Java, C#, and JavaScript all copy C's fall-through behavior exactly, for the same historical reason — inherited this design directly from C's original 1970s spec, and none of them changed it, because too much existing code already depended on it falling through by the time anyone might have wanted to fix it. Knowing this will not stop you from forgetting a break the first few times. The habit that does stop it: after you write the last line of a case's code, immediately ask "does this need to keep going into the next case, or does it need to stop here?" and write the answer — break; or a comment — before you move on, rather than after.

Grouping cases on purpose

Fall-through is not always a bug waiting to happen. Stack two or more case labels back to back with nothing between them, and you get a completely safe, common pattern: every one of those labels shares the same code, because execution "falls through" the empty labels with nothing to execute along the way.

int days_in_month(int month, int is_leap_year) {
    switch (month) {
    case 1:
    case 3:
    case 5:
    case 7:
    case 8:
    case 10:
    case 12:
        return 31;
    case 4:
    case 6:
    case 9:
    case 11:
        return 30;
    case 2:
        return is_leap_year ? 29 : 28;
    default:
        return 0;
    }
}

Seven separate month numbers all land on the same return 31;, because nothing sits between one case label and the next — there is no code to fall through, only more labels pointing at the same destination. This reads as one idea: "these seven months behave the same way," not seven repeated if branches. This chapter's first exercise asks you to write exactly this function. Notice, too, that return ends a case as finally as break does — either one hands control back out of the switch (and here, out of the function itself), so no case below a return can ever run by accident.

default does not have to be the last label written, either — the compiler accepts it anywhere among the cases, and it only runs when nothing above or below it matched. Every example in this chapter puts it last purely because that reads best: "if none of that, then this" is a more natural last line than a first one. Some languages that also have a switch-like construct — Swift and Rust's match, for instance — go further than C and refuse to compile a match that does not cover every possible value. C makes no such promise. switch (month) above only lists thirteen cases (twelve months and default); if default were left out entirely and month came in as 0 or 13, the switch would do nothing at all and execution would continue right past it — no error, no warning, only silence. A switch with no default is a bet that every value that can actually occur is already listed above it; get that bet wrong and the bug is an unhandled case that never even announces itself.

The difference between this section and the last one is not the syntax — both use fall-through, in the strict sense that execution can pass from one label into the next. The difference is whether anything runs in between. Empty labels stacked together cost nothing and hide nothing: every path they share is visible right there, one line apart. A case with real code and no break, like missing_break.c above, is where the danger lives — and where the next section shows you how to keep that same power without the accident.

The grouping only stays safe as long as the labels really do stay empty. Add so much as one line between two stacked case labels — even a comment containing real code you meant to keep, or a stray printf left over from debugging — and it now belongs only to the case above it, silently breaking the sharing you were relying on. case 1: case 3: printf("odd\n"); case 5: does not print for case 1 at all; it falls through into the printf only from case 3 onward. If a group of cases is meant to share nothing but a single trailing action, keep every label above that action completely empty, the way days_in_month does above.

Falling through on purpose, with code in between

Sometimes you want fall-through with actual code running along the way — a higher tier of something that should also get everything the tier below it gets. Writing this safely means being loud about it, so the next person reading the code (very possibly you, in six months) can tell instantly that a missing break was a choice, not a slip.

int bonus_points(int level) {
    int points = 0;

    switch (level) {
    case 3:
        points += 100;
        /* fallthrough */
    case 2:
        points += 50;
        /* fallthrough */
    case 1:
        points += 10;
        break;
    default:
        points = 0;
        break;
    }

    return points;
}
$ cc -std=c17 -Wall -Wextra -Werror -c bonus_demo.c
$ # bonus_points(1) -> 10
$ # bonus_points(2) -> 60   (50 + the 10 it falls into)
$ # bonus_points(3) -> 160  (100 + 50 + the 10 it falls into)

Level 3 membership is meant to include everything level 2 gets, which in turn includes everything level 1 gets — so case 3 adds its own 100 points and then deliberately falls into case 2's code, which adds 50 and falls into case 1's 10, which finally breaks. Delete either /* fallthrough */ comment and the code still runs identically — comments do not change what a compiler does. What they change is what a human reading this code six months from now believes. Without the comment, a missing break here looks exactly like the bug in missing_break.c above. With it, it looks like a decision. This is a real, widely used C convention, not a decoration specific to this course — you will see /* fallthrough */ or /* FALLTHROUGH */ in serious C codebases for exactly this reason. This chapter's second exercise asks you to write bonus_points yourself, with the fall-through doing the accumulating.

Newer compilers can warn about a case that falls through without any marker at all — a flag called -Wimplicit-fallthrough — specifically to catch the missing_break.c mistake automatically. This course does not enable that flag, so it will not catch a missing break for you here; treat the comment convention above as the habit to build by hand. C23 goes one step further and adds a real language attribute, [[fallthrough]];, that means the same thing as the comment but that a compiler can actually check. This course pins C17 (Module 0 explains why), so [[fallthrough]] is not available here — the comment is what you have, and it is what most existing C code still uses regardless.

break: leaving the nearest loop or switch

You already know break from last chapter's loops — it exits a while, do/while, or for loop immediately, skipping anything left in the loop body and anything left to iterate. Inside a switch, it does the same job for a different container: it exits the switch immediately, skipping every case below it, matched or not.

int sum_until_negative(const int *values, int n) {
    int total = 0;

    for (int i = 0; i < n; i++) {
        if (values[i] < 0) {
            break;
        }
        total += values[i];
    }

    return total;
}

Given {1, 2, 3, -1, 100}, this function adds 1, 2, and 3, then hits -1 and stops — the break exits the for loop right there, so 100 is never even looked at. This chapter's third exercise asks you to write this function. It is one break, in one loop, and it behaves exactly the way last chapter already taught you.

The one new wrinkle break has now that switch exists: break always exits the single nearest loop or switch that contains it — never both, even when one sits directly inside the other.

#include <stdio.h>

int main(void) {
    for (int day = 1; day <= 3; day++) {
        switch (day) {
        case 2:
            printf("Skipping day 2's switch cases.\n");
            break;   /* exits the switch, NOT the for loop */
        default:
            printf("Handling day %d\n", day);
            break;
        }
    }
    printf("Loop finished normally.\n");
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror switch_in_loop.c -o switch_in_loop
$ ./switch_in_loop
Handling day 1
Skipping day 2's switch cases.
Handling day 3
Loop finished normally.

A beginner reading case 2: above sometimes expects break; to jump out of the whole for loop, since a switch sitting inside a loop can look, at a glance, like one bigger block. It does not. break only ever knows about the one switch or loop wrapped most tightly around it — here, that is the switch, so the loop keeps going and prints day 3 right on schedule. If you actually need to exit the outer loop from inside a nested switch, C has no single keyword for it; the usual fix is a bool flag you check in the loop's condition, or (rarely, for exactly this case) goto, which cppreference's switch reference mentions as the one statement that can jump out of more than one level at once. Neither is needed for anything in this chapter — remember the rule itself: nearest enclosing loop or switch, never both.

The bool-flag fix mentioned above is worth seeing once, since it comes up again anywhere a nested loop or switch needs to signal something to an outer loop that break alone cannot reach:

#include <stdbool.h>
#include <stdio.h>

int main(void) {
    bool stop_everything = false;

    for (int day = 1; day <= 3 && !stop_everything; day++) {
        switch (day) {
        case 2:
            printf("Day 2 means stop the whole loop.\n");
            stop_everything = true;
            break;   /* still only exits the switch */
        default:
            printf("Handling day %d\n", day);
            break;
        }
    }

    return 0;
}

The switch's break still only exits the switch, exactly as before. What actually stops the for loop early is the loop's own condition, && !stop_everything, checked at the top of the next pass — the two keywords are not fighting each other, they are doing two separate, correctly scoped jobs.

continue: skipping to the next iteration

continue is break's quieter sibling. Instead of leaving a loop entirely, it skips the rest of the current pass through the loop body and moves straight on to the next one — the loop keeps running, it skips ahead past whatever code was left in this particular pass.

int count_letters(const char *s) {
    int count = 0;

    for (int i = 0; s[i] != '\0'; i++) {
        char c = s[i];

        if (c == '#') {
            break;
        }
        if (!((c >= 'a' && c <= 'z') || (c >= 'A' && c <= 'Z'))) {
            continue;
        }
        count++;
    }

    return count;
}

Every character that is not a letter — a space, a digit, a comma — hits the continue and skips straight past count++ for that one pass, without touching count at all. The loop does not stop; it moves on to the next character. A '#', by contrast, hits break and ends the loop completely — nothing after it is looked at, not even to check whether it is a letter. count_letters("ab#cd") stops the instant it sees '#' and returns 2; the "cd" that follows is never examined. This chapter's fourth exercise asks you to write count_letters yourself, using both keywords for the two different jobs they do.

One detail is easy to miss if you only skim continue's definition: inside a for loop specifically, continue does not skip the loop's own update step — the i++ in for (int i = 0; ...; i++) still runs every time, right after a continue, before the condition is checked again. If it did not, a continue at the top of a for loop's body would leave i frozen forever and the loop would never end. cppreference's continue reference states this precisely: in a for loop, continue jumps to the increment expression, not past it. In a plain while loop, where there is no separate update step built into the loop syntax at all, this same mistake is easier to make for real: a continue placed before a manual counter increment skips that increment on purpose or by accident, and an accidental skip is exactly how a while loop turns into the infinite loop last chapter warned you about.

continue only makes sense inside a loop — it has no meaning inside a bare switch that is not itself sitting inside a loop, and the compiler rejects it there. Written inside a switch that is nested inside a loop, continue ignores the switch completely and talks straight to the enclosing loop — the opposite of how break behaves in that same position, which stops at the nearest one. Worth remembering as a pair: break stops at the nearest loop or switch; continue always means the nearest loop, full stop.

Zooming out: from many paths to your own functions

You can now use switch to pick one path out of several exact values, explain why fall-through is C's default behavior rather than a bug, and use break and continue on purpose — including in the one surprising spot, a switch nested inside a loop, where they answer to two different enclosing blocks instead of one. That completes Module 2: you now have both of C's branching tools (if/else and switch), both of its ways to repeat work (while/do/while and for), and the two keywords that steer control inside either one.

Every function in this chapter's exercises was small and self-contained: given some numbers or a string, it computed one answer and handed it back with return. That was not an accident of these four exercises — it is a preview of Module 3. You have written main since chapter 1.1, and you have called functions the standard library already wrote for you, like printf and sizeof. Next chapter, you start writing your own, with your own parameters and your own return values — the exact shape every function in this chapter's tests/ already expected of your code, now explained from the inside.

One idea from this chapter reaches directly into that one. Every function here took its inputs — a month number, a membership level, an array of values, a string — without ever being able to change the caller's original copy of an int or a char. Only the array (sum_until_negative's values) and the string (count_letters's s) behaved differently, because both are handled through addresses rather than copies — ground Module 5 covers in full. Next chapter's outcome names this directly: C passes arguments by value, meaning a function normally receives a copy, not the original. You already relied on that fact every time you wrote switch (choice) in this chapter and trusted that nothing you did inside the switch could reach back out and change some other part of the program holding its own choice. Module 3 is where that quiet guarantee finally gets a name and an explanation.
