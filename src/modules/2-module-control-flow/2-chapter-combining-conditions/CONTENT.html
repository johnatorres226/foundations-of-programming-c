Last chapter you learned to write if/else if/else, and that C has no true boolean type: zero counts as false, and every other value counts as true. Every condition you wrote tested one thing at a time. This chapter combines several conditions into a single expression, and shows a rule about how C checks them that turns out to matter for more than saving keystrokes.

Big picture: why real decisions need more than one condition

Almost no real decision hangs on exactly one fact. A theme park lets you ride the roller coaster only if you are tall enough and the ride is not shut down for repairs. A smoke alarm should sound if smoke is detected or if someone forces a door meant to stay shut. A login screen should let someone in only if the password is right and the account has not been banned. Each of these is one decision built out of two or more smaller true/false facts.

You could write every one of these with nested if statements from the last chapter — an if inside another if, one fact per layer. Checking whether someone can ride the roller coaster, written that way, looks like this:

if (height_cm >= 120) {
    if (ride_is_open) {
        printf("you can ride\n");
    } else {
        printf("sorry, ride is closed\n");
    }
} else {
    printf("sorry, too short\n");
}

That works, but it grows clumsy fast. Four facts means four layers of nesting, two different "sorry" branches to keep straight, and a reader has to hold every open { in their head to see what the whole decision actually requires. The two "no" cases do not even agree with each other, even though from the rider's point of view they mean the exact same thing: not allowed. C gives you three operators that combine true/false conditions into a single expression instead: one condition, one decision, one reason for "no" when there is one to give. && ("and"), || ("or"), and ! ("not"). Together they are called logical operators — operators that work on true/false values, the way + and - work on numbers.

These three operators do more than tidy up your code. C makes a specific promise about the order it checks the pieces of an && or || expression, and that promise turns out to be a real safety mechanism — not a style choice. This chapter's second half is about that promise, called short-circuit evaluation, and why professional C code leans on it deliberately.

This matters more in C than it would in a language that checks array bounds or pointer validity for you automatically. C does neither. It trusts you to check first, and it gives you exactly the tools this chapter covers to do that checking in one expression instead of several scattered ones. A language that protects you from your own mistakes does not need this promise nearly as badly — C does, and leans on it constantly, in code you will read for the rest of this course.

&&, ||, and ! combine or invert true/false conditions into one expression, and C checks only as much of that expression as it needs to know the final answer.

How it works

The AND operator: &&

a && b is true only when both a and b are true. If either one is false, the whole expression is false. Remember from last chapter that in C, 0 is false and every nonzero value is true — that rule applies here too, on both sides of &&.

#include <stdio.h>

int main(void) {
    int value = 5, low = 1, high = 10;

    if (value >= low && value <= high) {
        printf("in range\n");
    } else {
        printf("out of range\n");
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror in_range_demo.c -o in_range_demo
$ ./in_range_demo
in range

Without &&, checking that value sits inside a range takes two separate if statements, one nested inside the other. With &&, both facts — "at least low" and "at most high" — become one condition that reads the way you would say it out loud: "value is at least low and at most high." && is not limited to two sides, either — a && b && c is true only when all three are true, and C checks them left to right, one at a time.

Whatever C prints for a && b is always exactly 0 or 1 — never a's or b's own value, even if those values are nonzero numbers like 5 or 200. C converts each side to true or false first, combines the results, and hands back a fresh 0 or 1. This chapter's exercise tests rely on that: a function built from && should always return 0 or 1, never one of its input numbers.

The OR operator: ||

a || b is true when at least one of a and b is true. It is only false when both sides are false.

#include <stdio.h>

int main(void) {
    int smoke_detected = 0, door_forced_open = 1;

    if (smoke_detected || door_forced_open) {
        printf("SOUND THE ALARM\n");
    } else {
        printf("all quiet\n");
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror alarm_demo.c -o alarm_demo
$ ./alarm_demo
SOUND THE ALARM

Notice that neither sensor here is "very true" or "true by itself" — one is 0 (false) and the other is 1 (true), and one true side is enough for || to make the whole condition true. A safety system built this way does not require every sensor to agree that something is wrong. Any one of them sounding off is reason enough to react. Like &&, || chains: a || b || c is true the moment any one of the three is true, and false only if all three are false.

The NOT operator: !

! flips a single true/false value to its opposite: !0 is 1, and ! of any nonzero value is 0. It reads as "not" — !is_banned reads as "not banned."

#include <stdio.h>

int main(void) {
    int is_banned = 0;

    printf("%d\n", !is_banned);   /* is_banned is 0 (false), so !is_banned is 1 */
    printf("%d\n", !5);           /* 5 is nonzero (true), so !5 is 0 */
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror not_demo.c -o not_demo
$ ./not_demo
1
0

! is most useful combined with && or ||, turning "and not" or "or not" into a single readable expression: has_correct_password && !is_banned reads as "the password is right, and the account is not banned" — exactly the rule a login screen needs, and exactly what this chapter's second exercise asks you to write.

! only ever inverts true or false, not the number itself. !5 is 0, not -5. A beginner sometimes reaches for ! expecting it to negate a number the way unary - does — it does not. If you want the negative of a number, use -x; if you want the opposite true/false answer, use !x.

A second trap with ! shows up as soon as it meets && or || inside parentheses. !(a && b) is not the same expression as !a && !b — flipping "both must be true" does not mean "both must be false." It means "at least one is false," which is !a || !b instead. If a is true and b is false, !(a && b) is true (their AND was false, so NOT of it is true), but !a && !b is false (!a is false, so the whole AND is false). The two expressions agree on some inputs and disagree on others — the safest way to negate a whole combined condition is to wrap it in !(...), exactly as written, rather than trying to distribute the ! across each piece by hand.

A very common beginner mistake looks like membership testing from other languages: if (choice == 1 || 2 || 3), hoping it means "choice is 1, 2, or 3." It does not. C reads each side of || as its own condition, so this is (choice == 1) || (2) || (3) — and 2 and 3 are nonzero, so they count as true all on their own, with no reference to choice at all. The whole expression is true for every value of choice, which the compiler will not warn you about, since it is perfectly legal C. The comparison has to be repeated on every side: choice == 1 || choice == 2 || choice == 3.

Short-circuit evaluation: why C stops early

Here is the promise C makes, and it is a promise, not an implementation detail that might change: when C evaluates a && b, it checks a first. If a is false, the whole expression is already false no matter what b is — so C never even looks at b. The same idea applies to a || b in reverse: C checks a first, and if a is already true, the whole expression is already true no matter what b is — so C never looks at b either. Skipping a side of the expression once the answer is already decided is called short-circuit evaluation: the check stops early, the same way an electrical short circuit takes a shortcut past the rest of a circuit.

#include <stdio.h>

int main(void) {
    int count = 0, total = 100;

    /* count is 0 (false), so && already knows the answer is false —
     * it never evaluates total / count, which would divide by zero. */
    if (count != 0 && total / count > 5) {
        printf("average is above 5\n");
    } else {
        printf("no count to average\n");
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror -fsanitize=address,undefined safe_divide_demo.c -o safe_divide_demo
$ ./safe_divide_demo
no count to average

Read that condition again with the order in mind: count != 0 is the guard — a condition checked first specifically to make it safe to check something else. Because count is 0, the guard is false, && short-circuits, and total / count never runs at all. Dividing by zero is undefined behavior in C — the program is allowed to do anything, including crash — and this line never gives it the chance.

|| short-circuits the same way, in the opposite direction: once the left side is already true, C never checks the right side. You can watch this happen instead of reading about it, by putting a printf inside the side that should get skipped:

#include <stdio.h>

int loud_check(int x) {
    printf("loud_check actually ran\n");
    return x > 0;
}

int main(void) {
    int cache_has_answer = 1;

    /* cache_has_answer is already true, so || already knows the answer.
     * loud_check() never runs, and its printf never fires. */
    if (cache_has_answer || loud_check(99)) {
        printf("using the cached answer\n");
    }
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror or_short_circuit_demo.c -o or_short_circuit_demo
$ ./or_short_circuit_demo
using the cached answer

"loud_check actually ran" never prints. If C evaluated both sides of every || no matter what, that line would appear before "using the cached answer" — it does not, because || already had its answer from the left side alone. This is the exact same proof this chapter's fourth exercise asks you to build yourself, with a counter instead of a printf.

Why short-circuiting matters for safety

Short-circuit evaluation is not only a performance trick that saves a computer a few microseconds. It is a pattern you can lean on to make risky operations safe: put the guard first, put the risky part second, and join them with &&. As long as the guard is written to fail exactly when the risky part would fail, the risky part never runs unless it is already safe to.

count != 0 && total / count > 5 is one example. You will meet the same shape again and again as this course continues: checking that an index is still inside an array before reading it (Module 4), checking that a pointer is not empty before following it (Module 5), checking that a file opened successfully before reading from it (Module 9). Every one of those is the same pattern as this chapter's division example — a cheap, safe check on the left, gating an operation on the right that would be unsafe or meaningless if the check had failed.

|| gives you the mirror image of the same trick: put a condition that already makes the risky check unnecessary on the left, and short-circuiting skips the right side. cache_has_answer || compute_the_slow_way() only calls the slow function when the fast cache does not already have what you need.

Programmers have a name for writing code this way on purpose: a guard clause — a condition placed early, specifically to make everything that follows it safe to run. You are not writing the guard and the risky operation as two separate steps that happen to sit near each other. You are writing one single expression where the guard's only job is to protect the second half, and C's order-of-evaluation promise is what makes that protection real instead of only hopeful.

This chapter's fourth exercise asks you to prove this to yourself, rather than take it on faith: a helper function counts how many times it actually runs, and your job is to write a guarded && expression that keeps that count at zero when the guard fails. There is no way to pass that test by accident — the count only stays at zero if short-circuiting genuinely skipped the call.

Short-circuiting only happens with && and ||. C also has single-character bitwise operators, & and |, that look similar but work on individual bits of a number and always evaluate both sides — no short-circuiting at all. Writing count != 0 & total / count > 5 with a single & would still divide by zero, because both sides run regardless. Module 14 covers what & and | actually do with bits; for now, the rule is simple: for combining true/false conditions, always use the doubled operators, && and ||.

Operator precedence: && binds tighter than ||

When an expression mixes && and || together, C groups the && parts first, the same way multiplication groups before addition in ordinary arithmetic — 2 + 3 * 4 is 14, not 20, because * binds tighter than +. Precedence is the name for that grouping order: && has higher precedence than ||, so it always grabs its two sides before || gets a turn.

Picture a store discount that should apply only to members, and only if they either have a coupon or hold VIP status. Written the way you might first reach for it, without parentheses:

#include <stdio.h>

int main(void) {
    int is_member = 0, has_coupon = 0, is_vip = 1;

    /* Intent: "a member, AND (has a coupon OR is VIP)".
     * Actual grouping, because && binds tighter than ||:
     *   (is_member && has_coupon) || is_vip
     * These are NOT the same rule. */
    int gets_discount = is_member && has_coupon || is_vip;

    printf("%d\n", gets_discount);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror discount_precedence_demo.c -o discount_precedence_demo
$ ./discount_precedence_demo
1

This customer is not a member at all — is_member is 0 — but the program grants the discount anyway, because is_vip is 1 and C grouped the expression as (is_member && has_coupon) || is_vip. Since || only needs one true side, a true is_vip alone is enough, with no requirement that this VIP is also a member. That may or may not be the rule the store actually wants — but it is not the rule the code reads like it wants, and that gap between what code says and what it does is exactly what precedence mistakes cause. The fix is parentheses around the part that must be evaluated as one unit:

int gets_discount = is_member && (has_coupon || is_vip);

With the parentheses, a non-member gets 0 no matter what has_coupon or is_vip say, because &&'s left side is already false — membership is checked first, and short-circuiting means the (has_coupon || is_vip) part is never even reached. When an expression mixes both operators, add parentheses around the part you mean to group, even in cases where you are confident you remember the precedence rule correctly. A reader should never have to recite a precedence table to know what your code means, and getting it wrong here does not crash the program or print a warning — it silently grants (or silently denies) something it should not.

Common mistakes

A few traps show up often enough with these operators to name directly, beyond the single-&/single-| mistake already covered above.

Writing = instead of == inside a condition. if (is_banned = 1) does not check whether is_banned equals 1 — it assigns 1 to is_banned, and the condition is true because the assignment's own result (1) is nonzero. This compiles without error and quietly changes a variable you only meant to read. Some compilers warn about it; -Wall catches many cases of it, which is one more reason this course always builds with it on.

Writing a chained comparison like math class taught you. 0 < x && x < 10 correctly checks that x is between 0 and 10. But 0 < x < 10, without the &&, is not a range check in C at all — it does not even fail to compile, which makes it worse. C reads it left to right: 0 < x is evaluated first, producing 0 or 1 (last chapter's rule again), and then that result is compared against 10. 0 < 10 and 1 < 10 are both true, so 0 < x < 10 is true for every value of x, including x = 500. This is exactly why this chapter's first exercise writes the range check as two comparisons joined with &&, never as one chained inequality.

Zooming out: from one true/false answer to a loop that keeps asking

You can now combine conditions with && and ||, invert one with !, and explain short-circuit evaluation: C checks the left side of && or || first, and skips the right side entirely whenever the left side has already decided the answer. You have also seen why that is not a minor efficiency detail — putting a safe guard on the left and a risky operation on the right is a pattern for writing code that cannot reach an unsafe operation by accident, and it is a pattern you will use for the rest of this course.

Every example in this chapter used && and || inside a single if, checked exactly once. Next chapter introduces while, do/while, and for — ways to make C check a condition and repeat a block of code for as long as that condition stays true. The conditions loops check are built from exactly the same material as this chapter: a loop like while (i < length && found == 0) combines two facts the same way in_range does, and short-circuiting matters here too — if i < length is already false, C never has to ask whether found == 0, because the loop is about to stop either way. The next chapter is about choosing the right kind of loop and making sure it actually terminates; the conditions that decide when to stop are conditions you already know how to write.

The guard pattern from this chapter's safety section is going to keep showing up, each time attached to a new kind of risk. Module 4 introduces arrays, and C never checks on its own whether an index is still inside one — reading or writing past the end is undefined behavior, exactly like the division by zero this chapter guarded against. The fix will look almost identical to count != 0 && total / count > 5: something like index >= 0 && index < length && array[index] ..., a guard checked first, an access that could go wrong second, joined by && so the unsafe access only runs once the guard has already confirmed it is safe to. Module 5 does the same thing for pointers: checking that a pointer actually points somewhere before following it. You already have the operator that makes both of these possible — what changes later is only what is being guarded against.

Two smaller threads from this chapter also carry forward. The precedence trap — && silently binding tighter than || — is the same kind of "the compiler accepts it, but it does not mean what it looks like it means" trap you will meet again with C's bitwise operators in Module 14, which reuse the single-character & and | this chapter told you to leave alone for logic. And the exercise that proved short-circuiting with a call counter is the same style of test you will write by hand in Module 11, when this course teaches testing as its own subject rather than something bundled quietly into every chapter's homework.
