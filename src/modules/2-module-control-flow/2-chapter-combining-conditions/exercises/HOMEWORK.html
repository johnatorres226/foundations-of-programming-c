Homework: Combining Conditions

You've learned how &&, ||, and ! combine and invert conditions, and how short-circuit evaluation makes a guard-then-act pattern genuinely safe rather than hopeful. Now put it into practice: four small functions, written from scratch in exercises/ and checked with make check-mine — not by reading this page.

exercises/01_in_range.c

Write a function int in_range(int value, int low, int high) that returns true only when value sits between low and high, with both ends counting as inside the range. in_range(1, 1, 10) and in_range(10, 1, 10) should both return true.

The chapter's "The AND operator: &&" section built exactly this check out of two comparisons joined with &&. Work out which two comparisons, and prove to yourself why one && is enough — you do not need a third condition.

A chained comparison like low <= value <= high, without the &&, compiles without complaint and is wrong for almost every input — see the chapter's "Common mistakes" section for exactly why. Write two separate comparisons, joined explicitly.

exercises/02_is_valid_login.c

Write a function int is_valid_login(int has_correct_password, int is_banned) that returns true only when the password is correct and the account is not banned. A banned account must never be let in, even with the right password.

The chapter's "The NOT operator: !" section showed ! paired with && to turn "and not" into one expression. Work out how that pairing applies here.

Do not write two separate return statements gated by an if/else before you have tried it as one expression — the whole point of this exercise is writing the check as a single &&/! combination, the way a login system in real code actually would.

exercises/03_should_sound_alarm.c

Write a function int should_sound_alarm(int smoke_detected, int door_forced_open) that returns true if either sensor has tripped — the alarm does not need both to agree.

The chapter's "The OR operator: ||" section covered this exact shape with the same two sensors. Prove to yourself that your function still returns true when both sensors are tripped at once, not only when exactly one is.

Remember that C's || always produces exactly 0 or 1, never one of the sensor values themselves — even if a caller passes something like 9 instead of 1 for "tripped."

exercises/04_no_wasted_work.c

Write a function int safe_to_proceed(int guard_ok, int value) so that when guard_ok is false, it returns false without calling expensive_check() at all — and when guard_ok is true, it returns whatever expensive_check(value) reports. The provided expensive_check_count counter is how the test proves whether expensive_check() actually ran.

The chapter's "Why short-circuiting matters for safety" section built this exact guard-then-act shape around total / count. Work out how to write safe_to_proceed as a single && expression, with the guard on the left — there is no way to pass the test with an if/else that calls expensive_check() unconditionally and only checks guard_ok afterward.

Stuck? Show one approach 
int safe_to_proceed(int guard_ok, int value) {
    return guard_ok && expensive_check(value);
}

This is one approach, not the answer. The important part is not the exact wording — it is that guard_ok sits on the left of &&, so a false guard stops C before it ever reaches expensive_check(value).
