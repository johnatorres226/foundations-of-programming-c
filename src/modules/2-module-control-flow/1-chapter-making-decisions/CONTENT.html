Last chapter you learned to read a compiler error, watch a breakpoint catch a wrong loop bound, and read an AddressSanitizer report catch a memory bug — three ways to find out that something already went wrong. Every program you have written so far ran the exact same steps in the exact same order, every single time, with no way to check anything and respond differently. This chapter gives your program its first way to decide: if, else if, and else, built on a rule with no dedicated true-or-false type behind it at all — zero counts as false, and every other number counts as true.

Big picture: why a program needs to choose, not only run straight through

Every program you have written in this course so far has had exactly one path through it. Line one runs, then line two, then line three, in the same order, no matter what numbers you feed it. That works fine for a program that only ever computes one fixed thing — an area, a sum, a printed sentence. It stops working the moment a program needs to react to something it cannot know in advance: was the number the person typed negative? Did the score pass? Is the temperature above freezing? A program that can only run straight through has no way to answer questions like that — it can only ever do the one thing it was written to do, regardless of what it is handed.

A condition is what fixes this: a question a program asks about a value it is holding, whose answer decides which lines run next and which ones get skipped entirely. A home thermostat is a condition running in a loop, forever: is the room colder than the target temperature? If yes, turn the heat on. If no, leave it off. The thermostat does not run both instructions every time and hope for the best — it checks, then picks exactly one path. That is the whole idea this chapter teaches you to write in C: check something, then run one block of code or another based on the answer.

Here is where C shows its age a little. Many newer languages ship with a dedicated boolean type — a value that can only ever be exactly true or exactly false, nothing else. C did not have one at all for its first thirty years. The earliest versions of C had no true or false keyword anywhere in the language — a condition was only a plain number, and the rule for reading it was short: 0 means false, and every other number, positive or negative, means true. C99 later added a way to spell true and false as words (you will see it below), but it did not change the underlying rule one bit — it only gave the same old numbers friendlier names. This is the same bargain you have met since Module 0: C hides less, and asks more of you, in exchange for control. A condition in C is never anything more mysterious than a number being zero or not.

The zero-or-not rule is not only a language quirk — it is close to how the hardware underneath actually works. Chapter 1.2 showed your source code passing through the compiler on its way to a runnable program. Deep inside that compiled program, a comparison like age < 18 becomes a CPU instruction that compares two numbers and sets a tiny piece of hardware state called a flag to 1 or 0 — "was the left side smaller, yes or no." The very next instruction, a conditional jump, reads that one flag and decides whether to skip ahead in the program or keep going in order. An if statement in your source code compiles down to exactly that: a comparison, a flag, and a jump. C's rule feels close to the machine because, at this one spot, it is the machine.

This chapter covers exactly three keywords built on that one rule: if, on its own; if paired with else, for exactly two paths; and a chain of if/else if/else, for choosing among more than two. It does not cover combining more than one condition in a single check with && or || — that is next chapter, once you can already write a single, solid condition on its own.

An if statement runs its block only when a condition — any expression that comes out nonzero — is true, and in C, zero is the only value that counts as false.

How it works

if — asking one question

An if statement is written as the word if, a condition in parentheses, and a block in { }. The block runs only when the condition is true; otherwise, the program skips straight past it, as if the block was never there at all.

#include <stdio.h>

int main(void) {
    int age = 15;

    if (age < 18) {
        printf("Not old enough to vote yet.\n");
    }

    printf("Program finished.\n");
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror age_check.c -o age_check
$ ./age_check
Not old enough to vote yet.
Program finished.

Change age to 20 and recompile, and the first line vanishes from the output entirely — the condition age < 18 is now false, so the block never runs. The last line, outside the if, prints either way, because it was never inside the block that the condition guards.

age < 18 is one of six relational and equality operators C gives you for building a condition — every one of them produces 1 or 0, ready to feed straight into an if:

Every one of these compares two values and never anything more than that. Combining two comparisons into a single condition — "is age at least 13 and under 20" — needs a different set of operators entirely, covered next chapter. For now, one comparison is one condition, full stop.

The { } around an if's block are easy to skip when the block is only one line — C allows it — but skipping them is the single most common trap beginners hit with if. Without braces, only the very next statement belongs to the if; every line after that runs no matter what, indentation or not:

if (age < 18)
    printf("Not old enough to vote yet.\n");
    printf("Enjoy the movie anyway.\n");   /* NOT part of the if! */

Indenting the second printf makes it look like it belongs to the if, but the compiler does not read indentation — it reads the semicolon that ends a statement. That second line runs for every age, always. Writing { } around every if's block, even a one-line one, is the single habit that prevents this bug outright, and this course's exercises expect it.

else — the other path

An if on its own only tells you what runs when a condition is true — the false path falls through with nothing happening. Adding else, with its own { } block, gives you the other path explicitly: exactly one of the two blocks runs, never both, never neither.

#include <stdio.h>

int main(void) {
    int age = 15;

    if (age < 18) {
        printf("Not old enough to vote yet.\n");
    } else {
        printf("Old enough to vote.\n");
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror age_check2.c -o age_check2
$ ./age_check2
Not old enough to vote yet.

Nothing here decides both messages could print, or neither could — that is exactly the guarantee if/else gives you over two separate, unconnected if statements. Two plain ifs that happen to test opposite conditions can drift out of sync if one of them is ever edited later; a single if/else pair cannot drift, because there is only one condition being tested, not two copies of it.

When if statements nest inside each other, an else always attaches to the closest unmatched if above it — not necessarily the one your indentation suggests. This is called the dangling else problem:

if (age >= 0)
    if (age >= 18)
        printf("Adult.\n");
else
    printf("Invalid age.\n");   /* attaches to "if (age >= 18)", not "if (age >= 0)" */

Despite how it is indented here, that else pairs with age >= 18, so a negative age prints nothing at all instead of "Invalid age." Wrapping every nested if in its own { } removes the ambiguity for a human reader and the compiler alike — another reason this course always writes the braces.

else if — chaining more questions

Two paths are not always enough. Stack else if between the first if and a final else to test more than one condition in order, top to bottom, and run the block belonging to the first one that turns out true:

#include <stdio.h>

int main(void) {
    int score = 82;

    if (score >= 90) {
        printf("A\n");
    } else if (score >= 80) {
        printf("B\n");
    } else if (score >= 70) {
        printf("C\n");
    } else {
        printf("Needs improvement\n");
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror grade_demo.c -o grade_demo
$ ./grade_demo
B

score is 82, which satisfies both score >= 80 and score >= 70 — but only "B" prints. The chain checks each condition in order and stops at the very first true one; every condition after that, even one that would also have matched, is never even evaluated. This is exactly the behavior this chapter's fourth exercise, grade_letter, asks you to build.

An else if chain is not the same as several separate if statements written one after another with no else connecting them. Stack three lone ifs instead of chaining them, and C dutifully checks every single one, every time — even after an earlier one already matched:

if (score >= 90) { printf("A\n"); }
if (score >= 80) { printf("B\n"); }   /* still checked and printed, even for score 95 */
if (score >= 70) { printf("C\n"); }   /* same here */

For score = 95, this prints all three letters, not one — because each if is its own independent statement with no memory of the ones before it. Chaining with else if is what creates "stop at the first match"; three bare ifs never do.

Here is a small but useful fact about C's grammar: else if is not its own keyword. It does not exist as a separate thing the language defines. It is really only an ordinary else whose entire block happens to be one single, nested if statement — and C already lets you drop the { } around a block that is only one statement long. Written out in full, without that shortcut, the grade example above is doing exactly this underneath:

if (score >= 90) {
    printf("A\n");
} else {
    if (score >= 80) {
        printf("B\n");
    } else {
        if (score >= 70) {
            printf("C\n");
        } else {
            printf("Needs improvement\n");
        }
    }
}

Both versions compile to the same program and behave identically — the else if spelling is only easier to read, since it avoids one more level of nested braces for every extra condition you add. Seeing the unrolled version once is worth it, though: it is the reason "stop at the first true condition" is true at all. Each else only ever runs when everything above it was false, and its whole job, at every level, is to ask one more question before giving up.

Zero is false, everything else is true

Every condition you have written so far — age < 18, score >= 80 — happens to be a comparison, which produces the whole number 1 when it is true and 0 when it is false. But if does not require a comparison at all. It accepts any expression that evaluates to a number, and the rule for reading that number never changes: 0 is false, and anything else — 1, -1, 42, -1000 — is true.

#include <stdio.h>

int main(void) {
    int count = -3;

    if (count) {
        printf("count is truthy\n");
    } else {
        printf("count is falsy\n");
    }

    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror truthiness_demo.c -o truthiness_demo
$ ./truthiness_demo
count is truthy

count is -3 here — negative, not the 1 a comparison would have produced — and the if still runs its true branch, because -3 is not 0. This is precisely the rule this chapter's third exercise, is_truthy, asks you to write out as a function of your own: return whatever answer C's own if would have given for that same number.

C99 added <stdbool.h>, a header that lets you write the words true and false and a type named bool instead of bare 1 and 0. It reads a little clearer in your own code, and this course uses it sometimes from here on — but it changes nothing underneath. bool is still stored as a small whole number, true is still exactly 1, and false is still exactly 0. Every rule in this section applies identically whether you write 0 or false, 1 or true — they are the same values wearing a friendlier name.

Because any nonzero number counts as true, testing a condition you meant to spell differently can silently "work" without ever failing loudly. A comparison that always evaluates to some nonzero number — even one that is not 1 — still takes the true branch every single time, with no warning from the compiler. C trusts that the number in the parentheses is the one you meant to test; it does not check whether a 0 was ever a real possibility.

This same rule is why C functions so often report a plain int "status" instead of a full word answer, and hand it straight to an if. Picture a function that looks through a list of names and reports how many times it found the one you were searching for:

int count_matches(void);   /* pretend this searches something and returns a count */

int main(void) {
    if (count_matches()) {
        printf("Found at least one.\n");
    } else {
        printf("Not found.\n");
    }
    return 0;
}

count_matches() is not a comparison — it is a whole number, the count itself, plugged directly into if. Zero matches is false, and any nonzero count, whether it is 1 or 50, is true. Real C code leans on this constantly: a function reports 0 for "nothing, none, not found," and the caller tests the result directly, with no separate comparison needed at all.

Chapter 1.3 showed that a char is really a small whole number underneath, and that rule reaches straight into truthiness too: if (letter) is true for every character except one whose underlying number happens to be 0 — a special value called the null character, written '\0', not the digit character '0', which is 48 and therefore true. This one distinction — '\0' is falsy, '0' is not — is exactly how C marks where a piece of text ends, once strings arrive in Module 4. The rule you are learning right now, "zero is false," is the same rule that quietly holds C's entire string system together later on.

Two traps: branch order and = vs ==

Two mistakes account for most of the bugs beginners write with if. Both compile without a single warning by default, and both produce a program that runs to the end and prints something — but not the right something.

The first trap is ordering an else if chain from loosest condition to tightest instead of the other way around. Since the chain stops at the first true condition, a broad check placed too early steals every case that a narrower, more specific check further down was supposed to catch:

int score = 95;

/* WRONG ORDER — score >= 60 is checked before score >= 90 */
if (score >= 60) {
    printf("D\n");
} else if (score >= 90) {
    printf("A\n");
}
$ cc -std=c17 -Wall -Wextra -Werror wrong_order.c -o wrong_order
$ ./wrong_order
D

A score of 95 clearly satisfies score >= 90 too, but the chain never reaches that check — score >= 60 already matched first, so the chain stops there. The fix is always the same: order an else if chain from the narrowest, most specific condition down to the broadest, so a broad catch-all condition never runs ahead of a more exact one it would otherwise shadow. This is exactly the trap this chapter's fourth exercise is built to catch if you get the order wrong.

The second trap is easy to type by accident and equally easy to miss reading it back: writing a single =, which assigns a value, where you meant ==, which compares two values for equality.

#include <stdio.h>

int main(void) {
    int x = 0;

    if (x = 5) {              /* assigns 5 to x, THEN tests 5 — always true */
        printf("x is 5\n");
    } else {
        printf("x is not 5\n");
    }

    printf("x is now: %d\n", x);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror assign_vs_compare.c -o assign_vs_compare
assign_vs_compare.c:6:10: error: using the result of an assignment as a condition
      without parentheses [-Werror,-Wparentheses]
    if (x = 5) {
        ~~^~~
1 error generated.

x = 5 is not a question at all — it is an instruction that stores 5 into x, and the result of that instruction is the value 5 itself, which if then reads as a condition. Since 5 is nonzero, the branch runs every time, no matter what x held a moment before — and x's original value is gone, overwritten. This course's -Wall -Wextra -Werror catches exactly this mistake and refuses to build, which is one more reason those flags are never optional in this course: a silent version of this bug, in a compiler without those warnings turned on, would run fine and lie to you forever. The fix is one extra character: if (x == 5) compares instead of assigning, and leaves x untouched.

One place C programmers really do assign inside a condition on purpose is worth knowing about, even though this course does not ask you to write it yet: wrapping the assignment in one extra pair of parentheses, like if ((x = getchar()) != EOF), tells the compiler "yes, I meant to assign here" and silences the warning, while a plain if (x = getchar()) would still trigger it. You will meet this exact pattern for real once file reading arrives in Module 9 — it reads one item, assigns it, and checks whether reading actually succeeded, all in a single line. For now, treat any unparenthesized = inside an if's parentheses as a typo until proven otherwise.

Zooming out: from asking one question to asking several at once

You can now write if, else, and else if, and explain exactly how C decides whether any given number counts as true: zero means false, and every other number — including every negative one — means true. That single rule is quiet but load-bearing. Every condition you write for the rest of this course, no matter how it is dressed up in comparison operators, function calls, or the logical operators coming next chapter, reduces to exactly this same zero-or-not check at the machine level.

Look back at this chapter's second exercise, max_of_three. Finding the largest of three numbers with only plain if/else forces you to nest one decision inside another — a condition inside a condition, several layers deep, only to combine two simple ideas ("is a at least b?" and "is a at least c?") into one check. That nesting is the exact seed of next chapter's subject: &&, ||, and ! let you combine several conditions into a single line, without nesting one if inside another at all, and you will learn a rule called short-circuit evaluation that decides, sometimes, not to check a later condition at all — which turns out to matter for more than tidiness. It is also how real C code safely checks "is this pointer usable?" before ever reading through it, a pattern you will meet properly once pointers arrive in Module 5.

Two more shapes of decision are still ahead, both built on the same true-or-false foundation this chapter gave you. Choosing between many exact, specific values — a menu option, a day of the week — gets its own dedicated tool, switch, in chapter 2.4, since a long else if chain of exact equality checks gets repetitive fast, and makes the branch-order trap this chapter already walked through easier to fall into with every condition you add. And every loop you write starting in chapter 2.3 — while, do/while, for — is a condition, checked over and over, deciding each time around whether to run its body once more, using the same zero-is-false rule and the same six comparison operators from this chapter, not a new set built specially for loops. You already know how to write that condition. What is new from here is everything C lets you build on top of it.
