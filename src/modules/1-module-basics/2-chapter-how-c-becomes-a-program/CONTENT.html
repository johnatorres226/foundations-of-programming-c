Last chapter you learned to read every token of a hello-world program: what #include, main, printf, and return each do. You typed one command and a runnable program appeared. This chapter opens up that command and shows the four separate jobs the compiler does, one after another, between your source file and a program you can run.

Big picture: why "compiling" is really four separate jobs

People say "compile the program" as if it were one step. It is not. Turning hello.c into hello is four separate jobs, run one after another, each one handing its output to the next: preprocess, compile, assemble, link. Each job reads one kind of file and writes a different kind of file. None of them can skip ahead or do another job's work.

Think of a factory line that turns logs into furniture. One station saws logs to rough length. The next station shapes each piece. The next joins the pieces into a chair. The last station sands and finishes it. A worker at the joining station cannot also do the sawing — the wood has to already be sawed before it reaches them. C's build line works the same way. Each of the four stages expects its input to already be in a specific shape, and it only knows how to do its own one job on it.

Why does this matter to you, a learner who types one cc command? Because every error message you will ever see from a C toolchain comes from exactly one of these four stages, and the stage tells you what kind of mistake you made. A missing header is a preprocess problem. A misspelled type is a compile problem. A missing main is a link problem. Once you know which stage produced an error, you stop guessing and start reading it correctly — the rest of this chapter is what makes that possible.

It also explains something you may already have noticed without a name for it: a tiny one-line change to hello.c recompiles almost instantly, but the whole process still touches four separate programs behind the scenes, not one. Each of those programs is small and does one job well — the classic Unix habit of building one big tool out of several small, focused ones chained together, instead of one program that tries to do everything.

Turning a .c file into a runnable program is four separate jobs — preprocess, compile, assemble, link — each one reading the previous job's output and handing its own output to the next.

How it works

Here is the whole pipeline in one picture before the detail. Follow one file, hello.c, through all four stations:

flowchart TD
  A["hello.c (source text)"] --> B["Preprocess"]
  B --> C["hello.i (expanded source text)"]
  C --> D["Compile"]
  D --> E["hello.s (assembly text)"]
  E --> F["Assemble"]
  F --> G["hello.o (machine code, not runnable alone)"]
  G --> H["Link"]
  H --> I["hello (runnable program)"]

One command, cc -std=c17 -Wall -Wextra -Werror hello.c -o hello, runs all four stages back to back and deletes the in-between files when it is done — which is exactly why the process has always looked like one step to you. Every stage below can also be run on its own, stopping the pipeline early on purpose, so you can see each in-between file for yourself.

Preprocess: text in, bigger text out

The preprocessor is the first stage, and it does not know any C at all. It only understands lines that start with # — called directives — and it does one job: text substitution. It reads your file, finds every directive, and follows it: paste in another file's contents, swap a name for other text, or delete a whole block of text before anyone downstream ever sees it. What comes out the other end is a longer file of plain C text, with every directive already carried out and gone.

#include <stdio.h>, which you met last chapter, is a preprocessor directive. "Read that file before you read the rest of mine" is a copy-paste instruction, nothing more — the preprocessor opens stdio.h and pastes its contents in, right where the #include line was. You can watch this happen. Stop the compiler after the preprocess stage with the -E flag, and it prints the expanded file instead of continuing:

$ cc -E hello.c | head -20

Most of what scrolls by is the pasted-in contents of stdio.h — dozens of lines you never wrote, describing every function that header offers, not only printf. Near the bottom, your own main function appears unchanged. That is the whole preprocess stage: paste, substitute, delete — never check whether any of it makes sense as C.

The other directive you will use constantly is #define, which names a piece of text so you can write the name instead of repeating the text everywhere. This is called a macro. The simplest kind, an object-like macro, names a single constant:

#define CRATE_SIDE 4

int crate_volume(void) {
    return CRATE_SIDE * CRATE_SIDE * CRATE_SIDE;
}

Run this through -E and every CRATE_SIDE is already gone, replaced by the plain digit 4, before the compile stage even starts:

$ cc -E crate.c | tail -3
int crate_volume(void) {
    return 4 * 4 * 4;
}

Nobody downstream — not the compile stage, not the assembler, not the linker — ever learns that the name CRATE_SIDE existed. It was a convenience for you, the person reading and writing the source file, and the preprocessor erased it on your behalf before anyone else looked at the text.

A macro is not a variable, even though CRATE_SIDE looks like one. A variable is something the running program can read and change. A macro is text pasted in before the program is even compiled — by the time crate_volume runs, CRATE_SIDE does not exist anywhere in memory to inspect. It was never more than three literal 4s.

The finished, all-directives-carried-out text the preprocessor produces has its own name: a translation unit. One .c file becomes exactly one translation unit — your own code plus every header it pulled in, pasted together into one long piece of text. Every stage after this one works on translation units, never on your original short file — which is worth knowing the next time an error message points at a line number that looks nowhere near anything you wrote; it may be pointing inside a pasted-in header instead.

#include also comes in two spellings, and the difference is not cosmetic. Angle brackets, #include <stdio.h>, tell the preprocessor to look in the compiler's own collection of standard headers — the ones that shipped with your toolchain. Double quotes, #include "helpers.h", tell it to look first in your own project's folders, for a header you wrote yourself. Mixing them up — quoting a standard header, or angle-bracketing your own — often still works, since most compilers fall back and search both places, but it states the wrong intention to anyone reading your code later. You will write your own headers starting in Module 10; for now, recognize the pattern: angle brackets mean "the compiler's own headers," quotes mean "look here in my project first."

C also has function-like macros — a macro that takes its own text argument and pastes it into a pattern, written with parentheses right after the macro's name and no space before them:

#define SQUARE(x) ((x) * (x))

int square_of_seven(void) {
    return SQUARE(7);
}

SQUARE(7) expands to ((7) * (7)) — the preprocessor copies the text 7 everywhere x appeared in the pattern. This looks exactly like calling a function, but it is still pure text substitution, with no idea what a number, a type, or an expression even is. That difference is not academic — it produces a real, well-known trap:

Drop the inner parentheses and write #define SQUARE(x) x * x instead. SQUARE(7) still expands to 7 * 7 and still gives 49 — looks fine. But SQUARE(3 + 4) expands to the literal text 3 + 4 * 3 + 4, not (3 + 4) * (3 + 4). Ordinary multiplication-before-addition order gives 3 + 12 + 4 = 19, not the 49 you wanted. The macro did exactly what it was told — paste this text in, unchanged — and the surrounding arithmetic reshuffled it. Every parameter and the whole expression need their own parentheses: ((x) * (x)), not x * x. This is the single most common macro bug in real C code.

The third directive worth knowing now is conditional compilation: #if, #ifdef, #else, and #endif. These let you write two versions of some code and have the preprocessor keep only one of them, deleting the other before the compiler ever reads it:

#define METRIC_UNITS 1

#if METRIC_UNITS
int box_capacity(void) {
    return 100;
}
#else
int box_capacity(void) {
    return 12;
}
#endif

Because METRIC_UNITS is 1, the preprocessor keeps the first box_capacity and deletes the second one, text and all, before compiling starts. Only one version of box_capacity ever reaches the compiler — there is never a moment where both exist at once. Flip the 1 to 0 and recompile, and the opposite happens: the second version survives and the first is deleted instead.

Because the deleted branch is never even read as C, it does not have to be valid C. You could write nonsense — misspelled keywords, unmatched braces, anything — inside the #else branch above, and the program still compiles cleanly as long as METRIC_UNITS stays truthy. This is a strong sign that preprocessing is a completely separate stage from compiling: text the preprocessor deletes is gone before any C rule is ever checked against it.

Put the three directives together and you have the whole job description of a preprocessor: #include pastes another file's text in, #define swaps a name for other text, and #if/#ifdef keep one block of text and delete another. Nothing here understands types, nothing here checks that braces match, nothing here knows what a function is. That checking is the next stage's job entirely.

Compile: text in, assembly out

This is the stage most people mean when they casually say "compiling," which is a little confusing now that you know it is only one of four stages sharing that name. Here it means one specific thing: turning preprocessed C text into assembly language — a text format that names the exact instructions one specific kind of processor understands, still readable by a person, but no longer C.

This is also the stage that actually reads C as a language, with all its rules. It checks that every name you use was declared. It checks that types make sense together. It is where "implicit function declaration," "expected a type," and most of the errors you saw last chapter come from — the preprocessor cannot produce those, since it never reads C rules at all, only directives.

Remember the misspelled prntf error from last chapter? That error came from this exact stage, not from a missing header. The preprocessor had already finished its job — every #include was pasted in, and printf was genuinely declared somewhere in that pasted-in text. The compile stage read your call to prntf, checked it against every name it now knew about, found no match, and refused. That is the pattern worth keeping: a preprocess error means text never arrived at all; a compile error means the text arrived, and something about it still breaks a rule of the C language itself.

Not every compile-stage complaint stops the pipeline. A warning is the compiler telling you something looks suspicious, then continuing anyway; an error is the compiler refusing to continue at all. Left to itself, a compiler lets many warnings through silently. This course always adds -Wall -Wextra -Werror for a reason: the first two flags turn on warnings the compiler would otherwise stay quiet about, and the third turns every one of those warnings into a hard error, so a suspicious line stops you the same way a broken one does. You are not seeing more mistakes than other C learners — you are seeing the same mistakes immediately, instead of finding them later as strange runtime behavior.

Stop the compiler after this stage with -S, and it writes the assembly text instead of continuing:

$ cc -S hello.c
$ head -6 hello.s
	.section	__TEXT,__text,regular,pure_instructions
	.build_version macos, 14, 0
	.globl	_main
	.p2align	4, 0x90
_main:
	.cfi_startproc

You are not expected to read assembly fluently — this course never asks you to write it. What matters is recognizing the shape: short instruction names, one operation per line, addressing real processor registers and memory. This is exactly one processor family's private, exact instruction list — the same hello.c compiled on a different kind of processor produces different assembly text, even though the C source never changed. C's whole promise of "write once, compile anywhere" lives in this stage: the compiler is the part that knows how to translate the same C meaning into whatever machine you are building for.

An error at this stage means your C is not valid C — a real language rule was broken, not only a missing file. This is different from a preprocess error like a missing header, which stops before any C rule is even checked. A compile-stage error is the compiler telling you: "I understood every #include and macro, and what came out still does not make sense as C."

Assemble: assembly in, machine code out

The assembler takes the assembly text from the previous stage and turns it into machine code: raw numbers, the actual bit patterns a processor executes directly. Assembly and machine code describe exactly the same instructions — assembly is the human-readable spelling of numbers the assembler now writes out.

Stop the compiler after this stage with -c, and it writes an object file — a file of machine code, ending in .o, that is not yet a runnable program:

$ cc -c hello.c
$ ls -la hello.o
-rw-r--r--  1 you  staff  656 Jan  1 00:00 hello.o

Try to run hello.o directly, and your operating system refuses — it is not shaped like a program the system knows how to start:

$ ./hello.o
zsh: exec format error: ./hello.o

An object file holds machine code for what you wrote — in this case, your version of main — but it is missing something specific: real, working machine code for printf. Your hello.c only declared that printf exists, back in stdio.h. It never wrote printf's own machine code, because you never wrote printf yourself — someone else already did, long before you compiled anything. Where that code lives, and how it gets joined to yours, is exactly what the last stage does.

You can see this hole directly. Every name an object file mentions — one it defines itself, or one it only calls and expects to find elsewhere — is called a symbol. A tool named nm lists an object file's symbols:

$ nm hello.o | grep -i printf
                 U _printf

U stands for undefined: hello.o mentions printf by name, but holds no machine code for it — only a note-to-self saying "something else needs to supply this." Run nm on the same file and look for main instead, and you see the opposite letter, T, meaning "defined, right here, in the executable code section":

$ nm hello.o | grep -i main
0000000000000000 T _main

The assembler's whole job stops there. It turns instructions into real bytes and keeps an honest list of which names still need to be found somewhere else. It never goes looking for printf itself — that search is the next stage's job, and only its job.

Machine code is specific to one kind of processor, and an object file carries that choice with it — the error message earlier in this chapter named it directly: architecture arm64. An object file assembled for one processor family cannot be linked with one assembled for another; the linker refuses instead of guessing. You will not hit this by hand in this course, but it is why a program built on one kind of computer sometimes needs a fresh rebuild, not a plain copy, to run on a different one.

Link: object files in, one program out

The linker takes one or more object files and produces one finished, runnable program. Your program almost never supplies every function it calls — you wrote main, but printf's actual machine code lives in a separately compiled collection of object files called the standard library, already sitting on your computer from when you installed your compiler. The linker's job is to find every function your object file calls but does not define, locate its real machine code in the standard library (or in any other object files you hand it), and stitch everything into one file with nothing left unresolved.

$ cc hello.o -o hello
$ ./hello
Hello, World!

That one command ran the linker directly on the object file you already had, since preprocessing, compiling, and assembling were already done in the previous step. The result, hello, is the first file in this whole chapter that your operating system will actually run — it carries real machine code for both main and printf, joined into one piece.

Put the last two stages together and the linker's job is exactly: read every U symbol the assembler left undefined, search the standard library's own object files for a matching T symbol with real machine code under that name, and copy that code in. Run nm again on the finished program instead of the object file, and printf's letter changes from U to T — proof the hole from the previous stage is now filled:

$ nm hello | grep -i printf
0000000100003f80 T _printf

A program can hand the linker more than one object file at once, and this is the one part of the whole pipeline that scales past a single .c file. Once you start splitting a program across several files of your own, in Module 10, you will compile each one to its own object file, then link all of them together in one command — the linker's job does not change at all, it resolves symbols across more object files instead of one file plus the standard library.

This is also where a whole category of error you have not seen yet comes from. Suppose you spell out printf's existence yourself, without ever #include-ing stdio.h or writing the function's body — the compile stage lets it through with only a warning, since older C allowed calling undeclared functions. But the linker cannot find real machine code for it anywhere:

$ cc broken.c -o broken
Undefined symbols for architecture arm64:
  "_printf", referenced from:
      _main in broken-a1b2c3.o
ld: symbol(s) not found for architecture arm64
clang: error: linker command failed with exit code 1

ld in that error is the name of the linker program itself — a strong clue this failure is not about your C syntax at all. "Symbol not found" means: I have a finished object file that calls something named printf, and I searched every object file and library I was given, and none of them contain real machine code under that name. Compiling succeeded. Linking is what failed.

A missing main produces this exact same kind of error, for the same reason. Every C program's own object file is missing one thing it needs from outside itself: the very first instruction the operating system will jump to. Normally your own main supplies it. Delete main entirely, and the linker reports it as an undefined symbol too — to the linker, "main" is not special syntax, only one more name it was asked to find, and this time could not.

Four stages, four different jobs, four different kinds of error. A missing or misspelled header is a preprocess problem — text that was never pasted in. A type mistake or a genuinely broken statement is a compile problem — text that does not follow C's rules. A missing -c input file is vanishingly rare to hit by hand, since the assembler almost never fails on its own once compiling succeeded. A missing function or missing main is a link problem — an object file with a hole in it that nothing else could fill. Knowing which of the four produced a given error message is most of what "reading a compiler error" means.

Zooming out: from a black box to the blanks variables fill in

The single cc command you have typed since chapter 0.4 was never one step. It is preprocess, compile, assemble, and link, run back to back, each stage handing a different kind of file to the next: text, expanded text, assembly, machine code, then one finished program. You have now watched every one of those in-between files appear on its own, with -E, -S, and -c, and you have seen the specific kind of error each stage produces when something goes wrong — a missing header at preprocess time, a broken statement at compile time, a missing function at link time.

Notice what this chapter's examples all had to work around: every value you computed was a fixed number, baked in with #define, because you have not yet met a way to store a number that can change while a program runs. That gap is deliberate. The next chapter introduces variables — named slots in memory that hold a value the running program can read and change — along with the handful of types C offers for them: int, char, float, and double. Where a macro is a name the preprocessor erases before compiling even starts, a variable is a name the compiled program keeps using the entire time it runs. You have now seen the whole pipeline that turns your text into a program; next you fill that program with values it can actually work with while it runs.
