Last chapter you learned to declare int, char, float, and double variables, and to predict each type's size with sizeof. Declaring a variable only gets a value into memory — this chapter is about getting values into that memory from outside the program, and printing what's in memory back out in a shape a person can actually read.

Big picture: why C makes you name the type at every input and output

A running program does not live alone. It prints results a person reads, and it reads values a person (or another program) types in. But everything crossing that boundary — everything typed at a keyboard, everything printed to a screen — is only text. A person types the characters 4 and 2, one after another; your program has to decide whether that text means the whole number 42, the two separate characters '4' and '2', or something else entirely. C never makes that decision for you. It never looks at a value and guesses what type it "probably" is.

Instead, C hands you two functions that act like a two-way translator at that boundary. printf takes a value already sitting in memory and turns it into readable text. scanf takes text a person typed and turns it into a value sitting in memory. Both work from the same idea: a format specifier is a short code, starting with %, that names the type of exactly one value — %d for a whole number, %f for a decimal number, and so on. You already met one specifier without being told its name: printf("Hello, World!\n") had no % in it at all, because every character in that string was meant to print exactly as written, with no value to fill in. The moment you want to print or read an actual variable, you have to say, out loud, what type it is — because nothing else in the program will say it for you. Get it wrong, and C does not stop you the way it stopped a missing header in chapter 1.1. It trusts you, and if you lied about the type, the result is undefined — anything from a wrong number on the screen to a program that crashes.

Think of a shipping label. The label does more than say "here is a box" — it states, up front, exactly what is inside and how much it weighs, so whoever opens it on the other end knows what to expect before they even cut the tape. A format specifier is that same idea, shrunk down to one value: %d is the label that says "a whole number is coming," %s says "text is coming." Nobody inspects the box's actual contents to double-check the label matches — the receiving end trusts what the label says and unpacks accordingly. That is exactly what printf and scanf do with your format string: they trust the label, every time, whether or not it happens to be true.

printf and scanf both work from a format string that names, one specifier at a time, exactly what type of value goes in each spot — and nothing checks that you told the truth.

How it works

The core printf specifiers: %d, %f, %c, %s

A format specifier is a placeholder inside a printf string. Everything else in the string prints exactly as written; each specifier is swapped out for one value, in order, from the list you give printf after the string. Four specifiers cover almost everything you will print in this course so far:

#include <stdio.h>

int main(void) {
    int count = 3;
    double price = 2.5;
    char grade = 'B';
    char name[] = "Sam";

    printf("%d apples cost $%f each. %s got a %c.\n", count, price, name, grade);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror specifiers.c -o specifiers
$ ./specifiers
3 apples cost $2.500000 each. Sam got a B.

%d prints an int as a whole number. %f prints a float or double as a decimal number — notice it printed six digits after the decimal point by default, even though price only had one; the next subsection shows you how to control that. %c prints a single char. %s prints a C string — text stored as a run of characters ending in a hidden null character, which you will study properly in Module 4. For now, treat char name[] = "Sam"; the way you already treat string literals: a fixed-size piece of text, sized for you by the compiler from what you wrote between the quotes.

Order matters, and count matters. printf fills specifiers left to right with the values you gave it, left to right, in the same order. Give it too few values for the specifiers in the string, or the wrong type for one of them, and nothing stops you at compile time by default the way a misspelled function name does — the mismatch is undefined behavior, meaning the program's next move is not something you can predict or rely on.

Modern compilers do try to help here: -Wall turns on -Wformat, which checks a printf call against its format string whenever the string is a literal written right there in your code. Swap %d for %s above and -Werror turns that warning into a hard compile error:

$ cc -std=c17 -Wall -Wextra -Werror specifiers.c -o specifiers
specifiers.c:8:13: error: format specifies type 'char *' but the argument
    has type 'int' [-Werror,-Wformat]
    printf("%d apples cost $%f each. %s got a %c.\n", count, price, name, grade);
            ~~                                         ^~~~~
            %s

This check only works when the format string is written directly in your code, so the compiler can read it at compile time. It cannot help you if the format string is built or chosen while the program runs — a case you will not meet until much later in this course.

Why does the type in a specifier matter this much? Because printf does not actually know the type of anything you hand it beyond what the format string tells it. Last chapter's sizeof showed that an int and a double do not even take up the same number of bytes in memory — typically 4 versus 8. Writing %d is not only picking a display style; it is telling printf exactly how many bytes to read starting at that spot, and how to interpret them: as a plain whole number, or as the very different bit pattern a floating-point number uses. Tell it %d for a value that is really a double, and printf reads the wrong number of bytes, from the wrong place, using the wrong recipe. That is the real reason the result is not only "a wrong-looking number" — it is undefined behavior: printf confidently misreading raw memory because you told it the wrong shape to expect.

One more specifier is worth knowing early: %% prints one literal percent sign. Since % starts every specifier, a lone % in a format string is ambiguous — %% is how you tell printf "I mean the character itself, not the start of a specifier."

Field width and precision: lining things up

A specifier can carry more than a single letter. A number right after the % sets a field width — the minimum number of characters that value takes up on screen, padded with spaces if it is shorter. A - right after the % switches the padding to the other side, left-aligning the value instead of the default right-alignment. A . followed by a number sets precision — for %f, exactly how many digits print after the decimal point.

#include <stdio.h>

int main(void) {
    printf("[%5d]\n", 42);    /* width 5, right-aligned  */
    printf("[%-5d]\n", 42);   /* width 5, left-aligned   */
    printf("[%05d]\n", 42);   /* width 5, zero-padded    */
    printf("[%.2f]\n", 2.5);  /* 2 digits after the dot  */
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror width_demo.c -o width_demo
$ ./width_demo
[   42]
[42   ]
[00042]
[2.50]

This is exactly what exercises/01_format_price.c and 02_format_row.c ask you to use: %02d to always show two digits of cents, even when the real value is 5 instead of 50, and %-10s together with %5d to line up a name and a score into neat columns, the way a receipt or a scoreboard would.

Width is a minimum, not a limit. %5d printing the number 140 does not cut it down to fit — three digits already meet the minimum of five once you count the two padding spaces, so nothing gets dropped. The same is true for %-10s with a name longer than ten characters: it prints the whole name, with no padding at all, because there was never room to add any. Field width only ever adds space; it never removes it.

Combine a few specifiers on one line and you get something that looks like a real receipt, not only an isolated number:

#include <stdio.h>

int main(void) {
    printf("%-10s%5d  $%6.2f\n", "apples", 3, 1.50);
    printf("%-10s%5d  $%6.2f\n", "bread", 12, 3.75);
    printf("%-10s%5d  $%6.2f\n", "milk", 1, 2.89);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror receipt.c -o receipt
$ ./receipt
apples        3  $  1.50
bread        12  $  3.75
milk          1  $  2.89

Every line uses the exact same format string, "%-10s%5d $%6.2f\n", with different values slotted in. That is the whole point of a format string: write the shape once, and every line that follows it lines up automatically, no matter how long the item's name is or how many digits its price has.

scanf, and the & it needs

scanf is printf's mirror image: instead of printing a value already in memory, it reads text and stores a value into memory. That difference in direction is exactly why scanf needs one thing printf never did — the address-of operator, &, written right before a variable's name.

#include <stdio.h>

int main(void) {
    int age = 0;

    printf("How old are you? ");
    scanf("%d", &age);
    printf("You are %d.\n", age);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror read_age.c -o read_age
$ ./read_age
How old are you? 9
You are 9.

Think about what printf("%d", age) needs versus what scanf("%d", &age) needs. printf only needs to read age's current value — handing it the value itself is enough. scanf needs to change age, and changing a variable from inside a function it did not create means telling that function where in memory age lives, not only what it currently holds. &age means "the address of age" — the location, not the content. You will get the full story on addresses and the variables that hold them, called pointers, starting in Module 5. For now, remember the rule as written: put & before the variable name for %d, %f, and %c. The one exception is %s into a char array — you will see why once you reach Module 4, but for this chapter's exercises, %d, %f, and %c are the ones you need, and all three need the &.

Forget the & and pass age instead of &age, and -Wformat (on by default with -Wall) usually catches it, the same way it caught a mismatched printf specifier earlier — scanf's %d expects an address (int *), and a bare int is not one:

$ cc -std=c17 -Wall -Wextra -Werror read_age.c -o read_age
read_age.c:6:12: error: format specifies type 'int *' but the argument has
    type 'int' [-Werror,-Wformat]
    scanf("%d", age);
           ~~   ^~~

Treat this error as a gift, not an annoyance. Without -Wall -Werror, a missing & can compile silently and corrupt memory instead — a much harder bug to track down than a compile error with a line number attached.

scanf also reports back how many values it actually managed to read, as its own return value — an int counting successful conversions, left to right, stopping at the first one that fails. Checking it is how a program tells the difference between "the person typed a number" and "the person typed something that was not a number at all," instead of silently carrying on with whatever age happened to hold before the call:

int age = 0;
if (scanf("%d", &age) != 1) {
    fprintf(stderr, "That wasn't a whole number.\n");
    return 1;
}

Both reference solutions for this chapter's scanf exercises check this return value before trusting what they read — a habit worth starting now, long before Module 9 covers error handling in depth.

Notice both examples above set age to 0 the moment it is declared, before scanf ever runs. That is not decoration. If scanf fails to read anything — the person typed letters instead of digits, say — it leaves age completely untouched. An uninitialized int holds whatever bits were already sitting in that memory, which is not predictable. Giving it a starting value first means a failed read leaves you with a known, sane number instead of whatever garbage happened to be there — the same reason chapter 1.3 had you initialize variables at all.

Reading more than one value works the same way printf did: list a specifier for each value you want, and a matching address for each one, in the same left-to-right order:

int quantity = 0;
double price = 0.0;

scanf("%d %lf", &quantity, &price);

%f and %lf look almost the same, and beginners mix them up constantly, in the wrong direction each time. In a printf call, %f alone is correct for a double — C automatically widens a float argument to double before printf ever sees it. In a scanf call, the rule flips: %f reads into a float, and you need %lf ("long f") to read into a double. scanf is writing directly into memory of a specific size through the address you gave it, so it has no automatic widening to lean on the way printf does. Mix them up and you get the same kind of silent memory misread as any other specifier/type mismatch.

scanf's %s has its own sharp edge, worth knowing about even though this chapter's exercises avoid it: written bare, with no width limit, %s keeps reading and writing characters into your buffer for as long as non-whitespace characters keep coming — with no idea how big that buffer actually is. Type more characters than the buffer can hold, and scanf happily writes past its end anyway.

char name[8]; scanf("%s", name); looks harmless, but typing a name longer than 7 characters (the 8th slot is reserved for the string's hidden terminator) overflows name and starts overwriting whatever memory sits right after it — a real bug class, not a theoretical one, and one you will meet again in Module 4. The fix is a width limit inside the specifier itself, matched to the buffer's real size: scanf("%7s", name) for that same 8-byte buffer stops itself one character early, on purpose, to leave room for the terminator.

Why scanf skips blanks — and why %c doesn't

Typed input is full of characters a person never thinks about: the space between two numbers, the newline left behind by pressing enter. %d, %f, and %s all skip any amount of leading whitespace — spaces, tabs, and newlines — before they start reading the value you asked for. That is why two numbers typed on the same line, separated by a space, and the same two numbers typed on two separate lines, both work with the exact same scanf("%d %d", &a, &b) call:

$ ./sum_two_numbers
3 4
Sum: 7
$ ./sum_two_numbers
3
4
Sum: 7

%c is the one specifier that breaks this pattern on purpose. It reads the very next character sitting in the input, whatever it is — including a leftover space or newline from something typed earlier. It never skips whitespace, because for %c, whitespace is a perfectly valid answer.

See it happen with a small menu prompt — read a number, then read a single letter that is supposed to be the person's next choice:

#include <stdio.h>

int main(void) {
    int score = 0;
    char choice = 0;

    printf("Enter your score: ");
    scanf("%d", &score);

    printf("Continue? (y/n): ");
    scanf("%c", &choice); /* grabs the leftover '\n', not 'y' or 'n' */

    printf("You typed: '%c'\n", choice);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror menu_bug.c -o menu_bug
$ ./menu_bug
Enter your score: 87
Continue? (y/n): y
You typed: '
'

The person typed y, and the program printed a newline instead. The y is still sitting in the input, unread — the %c call finished before it ever got there, because the leftover '\n' from pressing enter after 87 was the very next character waiting.

The fix is one character: a space before %c in the format string, scanf(" %c", &choice), tells scanf to skip whitespace first, the same way %d already does. That single space is doing real work — it is not there for style.

The trap: a leftover newline breaks the next read

The same leftover-newline problem shows up in a second, more common shape: reading a number with scanf("%d", ...), then reading a whole line of text — someone's name, which might contain a space — with fgets. You will study fgets properly in Module 9; for this chapter, know that it reads everything up to and including the next newline, into a buffer you give it.

Here is the trap in full. scanf("%d", &age) stops the instant it has read the digits of the number — it does not read the newline that comes right after them. That newline is still sitting in the input, waiting. If the very next thing you call is fgets, it finds that leftover newline immediately, decides the "line" is already over, and hands you an empty string instead of the name you wanted:

int age = 0;
char name[64];

scanf("%d", &age);
fgets(name, sizeof(name), stdin); /* reads the leftover '\n', not the name */

The fix is to throw away that leftover newline yourself before calling fgets, one character at a time, until you have consumed it:

int age = 0;
char name[64];

scanf("%d", &age);

int c;
while ((c = getchar()) != '\n' && c != EOF) {
    /* discard everything up to and including the leftover newline */
}

fgets(name, sizeof(name), stdin); /* now reads "Rex\n" for real */
$ ./name_and_age
9
Rex
Rex is 9 years old.

Notice this trap needs fgets or getchar specifically — chaining two ordinary scanf numeric or %s reads back to back never hits it, because %d, %f, and %s all skip leading whitespace on their own, the same way you saw earlier with two numbers split across separate lines. The trap only appears the moment you mix a scanf call with something that reads whitespace-sensitively right after it — fgets and the bare %c you met a moment ago are the two you will meet most often in this course.

This is the exact shape exercises/04_name_and_age.c asks you to build. The bug this trap causes is a particularly nasty one to meet on your own: the program compiles perfectly clean under -Wall -Wextra -Werror, and it runs without crashing. It silently produces the wrong answer instead, which is the kind of bug that teaches you why "it compiled" and "it works" are two completely different claims.

getchar() reads and returns one character from the input as an int, not a char — that is why c above is declared as int. The reason is EOF, a special value getchar returns when there is nothing left to read at all. EOF has to be a value no real character could ever equal, and a plain char cannot always represent every value int can — so getchar() widens its answer to int to leave room for EOF to mean exactly one thing: "the input is over," never mistaken for a real character.

Zooming out: from typos the compiler catches to bugs it can't

Every trap in this chapter shared one shape: the program compiled without a single warning, ran without crashing, and still produced the wrong answer, or the right answer by luck. A mismatched printf specifier and a missing & were the exceptions — -Wall -Wextra -Werror caught both of those for you, at compile time, before the program ever ran. The leftover-newline trap was different: nothing in the compiler could catch it, because nothing about scanf("%d", &age) followed by fgets(...) is technically wrong. Both calls are individually correct. The bug only exists in how they interact, at runtime, with a specific shape of input — and that is a whole category of bug the compiler was never designed to see.

Next chapter is about exactly that gap. You will learn to read a compiler error message properly instead of skimming past it, set a real breakpoint in a debugger so you can pause a program mid-run and look at what its variables actually hold, and run a program under AddressSanitizer — a tool built to catch the class of bug that compiles clean and runs clean, right up until it doesn't. The leftover-newline bug you fixed by hand a moment ago is a small, friendly preview of a much larger idea: some bugs only exist while the program is running, and finding them takes different tools than the ones that caught your typos.

Zoom out even further and the shape of this chapter repeats everywhere. Every program that reads a configuration file, accepts a command-line flag, or takes a form submission on a web server is doing exactly what exercises/04_name_and_age.c does: turning outside text into typed values, and having to survive whatever shape that text actually arrives in, not only the shape you hoped for. scanf is the small, first version of a problem you will meet again and again for the rest of this course.

Hold on to this chapter's core idea, too, because it does not go away once you stop thinking about it consciously: every format string is a set of promises about type, and C checks none of them for you at runtime. -Wall -Wextra -Werror catches the promises you can check before the program ever runs — a mismatched specifier, a missing &. The promises that only break once real input arrives are the ones that need a different kind of tool, and finding those is what the next chapter is for.
