Last chapter you installed a working C compiler and ran one program to prove your toolchain works. That program was five short lines that looked like magic. This chapter opens it up and explains what each line does, word by word.

Big picture: why every C program states the same pieces up front

C does not guess what your program needs. The operating system that runs your program needs to know exactly where it should start, and the compiler needs to know exactly which tools you plan to borrow before it lets you use them. Every C program states both things up front, in the same handful of pieces, in the same order. Learn to read those pieces once and you can read the first few lines of almost any C program you meet next, in this course or anywhere else.

Think of a recipe card. Before any cooking step, it lists the tools you need and the ingredients you are borrowing from the pantry. Then it names one clear starting point — "preheat the oven" — so two cooks reading the same card start in the same place. Then come the actual steps, in order. Then a note on what "done" looks like. A C program is shaped the same way: borrow your tools first, name one starting point, do the steps, report how it went. Nothing here is unique to hello.c — this shape is the skeleton every C program you write for the rest of this course will share.

A hello-world program is four required pieces — an #include line, a main function, a printf call, and a return — and each piece does exactly one job.

How it works

Here is the program from last chapter again, in full:

#include <stdio.h>

int main(void) {
    printf("Hello, World!\n");
    return 0;
}

Five lines, four jobs. Here is what each one is doing.

#include <stdio.h>

A header file is a file full of information the compiler needs about functions someone else already wrote. #include tells the compiler "read that file before you read the rest of mine." stdio.h stands for standard input/output — it describes functions for reading and printing text, including printf. Without this line, the compiler has never heard of printf and refuses to compile your program.

stdio.h is one header among many. C ships a whole standard library — a large set of ready-made functions every C compiler provides — split into header files by topic, so you only borrow what a given program actually needs. stdlib.h holds general-purpose functions like converting text to numbers. string.h holds functions for working with text. math.h holds functions like square root and rounding. As one concrete taste: stdlib.h's atoi function turns text like "42" into the actual number 42 — useful the moment your program needs to read a number a person typed in, since everything typed at a keyboard arrives as text first. You will meet all three headers properly later in this course; for now, recognize the pattern: one line, #include <header_name.h>, borrows one topic's worth of tools.

Some languages hand every program a large set of built-in tools automatically, whether that program uses them or not. C does the opposite on purpose: you name exactly what you are borrowing, one header at a time. That has a real cost — you have to know which header a function lives in before you can use it — but it also means a C program only carries the weight of what it actually uses. This is the same trade-off you met in Module 0: C hides less from you, and asks more of you, in exchange for control.

Delete the #include line and try to compile, and the compiler stops you before your program ever runs:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:2:5: error: call to undeclared library function 'printf' with type
    'int (const char *, ...)'; ISO C99 and later do not support implicit
    function declarations [-Wimplicit-function-declaration]
    printf("Hello, World!\n");
    ^
hello.c:2:5: note: include the header <stdio.h> or explicitly provide a
    declaration for 'printf'

The compiler is not guessing what printf means — without #include <stdio.h> it has never been told printf exists at all, so it refuses to compile rather than assume.

Misspell the header name instead of leaving it out, and you get a different error, for a different reason. The compiler needs to physically open and read that file before it can do anything else, so a header name it cannot find fails immediately — before it even looks at the rest of your program:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:1:10: fatal error: 'stdiot.h' file not found
    1 | #include <stdiot.h>
      |          ^~~~~~~~~~
1 error generated.

fatal error is the compiler's way of saying "I cannot continue at all" — compare that to an ordinary error, which still lets the compiler keep reading the rest of the file to see if it can find more problems worth reporting at once. A missing header stops everything on the spot, because nothing after it can be checked without knowing what that header would have defined.

int main(void)

A function is a named block of code that runs when something calls it. main is special: it is the one function every C program must have, and it is the first function that runs — nothing calls it, the operating system does. The int in front says main reports back a whole number when it finishes. The (void) says main takes no information in from whatever starts it.

"The operating system calls it" is not a figure of speech. When you type ./hello and press enter, the operating system — Windows, macOS, or Linux — loads your compiled program into memory and jumps straight to the address where main lives. Every other function in a C program is called by name, somewhere in your own code, by something you wrote. main is the one exception: nothing in hello.c calls it, because it is the starting line the operating system was already looking for. A later module covers exactly how the operating system finds that address — for now, remember the rule: a C program needs exactly one main, or the operating system has nowhere to begin.

"Exactly one" cuts both ways — a file with zero main functions has nowhere to start, and a file with two is equally broken, for a different reason. The compiler cannot pick between two functions with the same name, so it refuses both:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:8:5: error: redefinition of 'main'
hello.c:3:5: note: previous definition is here

This is not special to main — no two functions in the same C program can share a name. main happens to be the one you are guaranteed to write in every single program, so it is the one you will see this mistake with first.

(void) is doing real work in that line, not filling empty space. A function's parentheses are where it lists what information it needs to do its job — its parameters. A function that adds two numbers might start int add(int a, int b), naming two whole numbers it needs before it can run. Writing void instead is how you say, on purpose, "this function needs nothing handed to it." You will write functions with real parameters starting in Module 3 — for now, recognize the shape: name goes first, then parentheses holding whatever the function needs, empty or not.

Real C files also carry comments: text meant only for a person reading the code, which the compiler skips entirely. // starts a comment that runs to the end of that line. /* ... */ starts a comment that can span several lines, ending at the matching */. Neither shows up in the program's output — they exist only in the source file:

#include <stdio.h>  // borrow printf

/* This is the traditional first program in almost every language.
   Printing a fixed message proves your toolchain compiles and runs. */
int main(void) {
    printf("Hello, World!\n");
    return 0;
}

This compiles to the exact same program as the version without comments — the compiler deletes every comment before it does anything else. Comments exist for you and for anyone else who reads your code later, including you in six months, after you have forgotten why a line was written the way it was.

A /* with no matching */ does not stop at the end of the line the way // does — it swallows everything after it, including real code, until it finds a closing */ somewhere later in the file. A missing closing marker can turn working code into one giant comment, and the errors the compiler reports will point at the wrong lines entirely.

printf("Hello, World!\n");

This line calls the printf function — the parentheses are what "calling" a function looks like in C, and they hold the information you are handing it. Here, that information is a string literal: text wrapped in double quotes, printed exactly as written. The two characters \n inside it are one escape sequence — a backslash followed by a letter that means something other than the letter itself. \n means "move to a new line." It does not appear in the output; it controls where the next thing printed will go. The semicolon at the end marks where this instruction, called a statement, finishes. C does not care about line breaks — only the semicolon tells it a statement is done.

\n is the escape sequence you will use the most, but it is not the only one. \t prints a tab — useful for lining up columns of text. \\ prints a single literal backslash, for the same reason \" exists: a backslash normally starts an escape sequence, so printing a real one needs its own escape. \r, a carriage return, moves back to the start of the current line without starting a new one — rare in your own code, but worth recognizing, since older Windows text files end every line with \r\n instead of the plain \n this course uses. You will meet the rest of the list as you need them.

Forget the semicolon and the compiler cannot tell where one statement ends and the next begins. It will report an error, usually pointing at the line after the one you actually forgot it on — that confuses almost everyone the first time.

The parentheses matter as much as the name. Misspell printf — say, prntf — and the compiler does not guess what you meant. It refuses to compile, the same way it refused when #include <stdio.h> was missing:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:4:5: error: call to undeclared function 'prntf'; ISO C99 and later
    do not support implicit function declarations
    [-Wimplicit-function-declaration]
    prntf("Hello, World!\n");
    ^
hello.c:4:5: note: did you mean 'printf'?

Notice the compiler's own guess at the end: did you mean 'printf'?. Many compilers try to spot a typo of a name they do recognize and suggest it. That note is a hint, not a fix — you still have to correct the spelling yourself and compile again.

A program can call printf more than once. Each call is its own statement, and statements run in the order they are written, top to bottom. Two calls, each ending in \n, print two separate lines:

printf("First line.\n");
printf("Second line.\n");
$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
$ ./hello
Hello, World!

A string literal can hold almost any character, but a double quote is a problem — it looks like the end of the string. Put a backslash in front of it, \", and printf prints a real double quote instead of ending the string early:

printf("She said \"hello\" back.\n");

A stray, un-escaped " in the middle of a string literal ends the string right there. Everything after it confuses the compiler, which then reports an error somewhere that looks unrelated to the real mistake.

This is also why \n exists instead of pressing enter directly inside your quotes. A string literal in C cannot contain a real line break — only the two characters \ and n, standing in for one. Press enter for real, and the string never finds its closing quote on the same line, which confuses everything that follows it, one error stacking on the next:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:4:12: error: missing terminating '"' character
hello.c:5:9: error: missing terminating '"' character
hello.c:7:2: error: expected '}'
4 errors generated.

One real mistake — a stray line break — produced four reported errors. This is common enough to name: a single early mistake confuses the compiler about everything that comes after it, so it reports several errors that all trace back to one root cause. When you see a wall of errors, always fix the first one and recompile before reading the rest — the others often disappear on their own.

return 0;

This is the last statement main runs. return ends the function and hands back the number that follows it — this is the whole number int main promised earlier. That number is called an exit status: a report to whatever started the program about how it went. By convention, 0 means "everything worked." Any other number means "something went wrong." You will not use this number much yet, but tools that run your program automatically — including the ones that check your exercises in this course — read it to decide whether your program succeeded.

You can see this number yourself. Most terminals keep the last program's exit status in a variable named $?:

$ ./hello
Hello, World!
$ echo $?
0

Change return 0; to return 1;, recompile, and run it again — echo $? now prints 1. The text your program prints and the number it returns are two completely separate things: one is for a person reading the screen, the other is for whatever program ran yours next.

This is not a hello-world curiosity — real command-line tools use exit status constantly, and you have probably relied on it without noticing. Ask a file manager for a file that does not exist, and it complains loudly and returns a nonzero status:

$ ls /a/path/that/does/not/exist
ls: /a/path/that/does/not/exist: No such file or directory
$ echo $?
1

Scripts that run one command after another often check $? before running the next one, so they can stop instead of continuing on top of a failure. Your hello-world program returning 0 is the same signal, in miniature: "I finished, and nothing went wrong."

Leaving off return 0; entirely is not the same mistake as forgetting a semicolon elsewhere — modern compilers assume a missing return at the very end of main means "everything worked" and fill in 0 for you. That rule applies to main only. Every other function that promises to return a number and does not is a real bug, and -Wall will warn you about it.

Closing brace

The { after int main(void) opens the block of statements that belong to main; the matching } at the end closes it. Every opening brace in C needs exactly one matching closing brace.

The compiler does not care how you arrange whitespace around that brace, or how far you indent the lines between it and its match. All three programs below compile to the exact same output:

int main(void) { printf("Hi\n"); return 0; }
int main(void)
{
        printf("Hi\n");
        return 0;
}

This course writes every example the way you saw at the top of this chapter: the opening brace on the same line as main, and each statement inside indented four spaces. That is one style among several real ones used in professional C code, not a rule the compiler enforces. What indentation buys you is not correctness — it is a reader's ability to see, at a glance, which lines belong inside which block, without counting braces by hand. Pick a style, including this course's, and hold it steady across a whole file; the value is in the consistency, not in which style you picked.

The brace itself is not optional the way its position on the line is. Delete the closing } and the compiler notices immediately — it reads to the end of the file still waiting for a block to close, and tells you exactly where the unmatched opening brace was:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello
hello.c:6:1: error: expected '}'
hello.c:3:16: note: to match this '{'

That second line, starting with note:, is the compiler pointing back at the specific opening brace it thinks is missing its match — worth reading before you go hunting through the whole file yourself.

Reading the compile command

You have typed this command since chapter 0.4 without a full explanation of each piece. Now that you can read the file itself, it is worth reading the command that turns it into a program, too:

$ cc -std=c17 -Wall -Wextra -Werror hello.c -o hello

cc is the name of the compiler you are running. -std=c17 tells it which rulebook to follow (chapter 0.3). -Wall -Wextra -Werror turn on extra warnings and treat every one as an error (chapter 0.4) — both of the compiler errors earlier in this chapter appeared because of these flags. hello.c is the input: the source file to read. -o hello names the output: the runnable program to create, called hello.

Leave off -o hello entirely, and the compiler still works — it falls back to a default output name, a.out, instead of asking you what to call it. a.out stands for "assembler output," a name left over from decades-old Unix tools; it survives purely as a default, not because it means anything useful today. This course always names the output explicitly with -o so it is easy to know what to run next.

The .c at the end of hello.c is not decoration — it tells the compiler this file holds C source code to translate. Rename the exact same file to hello.txt and hand it to the compiler, and it no longer recognizes the file as something to compile at all:

$ cc -std=c17 -Wall -Wextra -Werror hello.txt -o hello
ld: unknown file type in 'hello.txt'
clang: error: linker command failed with exit code 1

The error comes from the linker, a later stage you will meet next chapter — the compiler skipped straight past "translate this" and tried to treat the file as something already translated, because the name did not end in .c. Header files carry their own matching convention, .h, for the same reason: the extension is how every tool in the toolchain agrees on what kind of file it is looking at, without opening and guessing from its contents.

Put the six pieces back together and check yourself: could you point to the line that borrows a tool, the line that names the starting point, the line that does the actual work, and the line that reports back? Could you say, from memory, what happens if any one of them is missing or misspelled? If any of those feel shaky, scroll back to that subsection before moving on — every later chapter in this course assumes you can read this exact shape without stopping to think about it.

Zooming out: from reading tokens to watching the compiler work

You can now read every token of a hello-world program: what #include borrows, what main starts, what printf prints, and what return reports back. You also know the recipe-card shape behind all of it — borrow your tools, name a starting point, do the work, report how it went — and you have seen the compiler enforce every piece of it: refusing a missing header, refusing a misspelled function name, filling in a default only for main and nowhere else. None of that was the compiler being strict for its own sake. Each refusal traced back to the same idea from this chapter's big picture: C does not guess.

What you have not seen yet is what the compiler does with that text between the moment you save hello.c and the moment ./hello runs. Right now that process is a black box: text goes in, a runnable program comes out. The next chapter opens that box: preprocess, compile, assemble, link — four steps, and what the compiler is actually doing at each one.

Scale matters here too. A real program you might install tomorrow can be hundreds of thousands of lines across many files, written by hundreds of people over many years. It still borrows its tools, still has exactly one starting point, still does its work, and still reports back when it finishes — the same shape as hello.c, only much larger. You will not write anything that big in this course, but every program you do write, all the way through the capstone project, is built from this same skeleton.
