Last chapter followed one line of C through the compiler's four stages — preprocess, compile, assemble, link — and showed what the compiler does at each one, all before that line ever runs. This chapter looks at what a line like that is actually describing: the values a C program holds, and the fixed size and shape C gives every one of them before it can be used.

Big picture: why C makes you pick an exact size for every value

Every value a running program holds — a person's age, a temperature, a single letter — has to live somewhere in memory. Memory is a fixed, finite resource: a computer has a specific number of bytes, not an endless supply. Some languages hide this from you. They let a number grow as large as it needs to, quietly reserving more memory behind the scenes whenever a value gets bigger. That convenience has a cost: the language has to check, every time, whether the current amount of memory is still enough, and grow it if not.

C does not do this. When you declare a variable in C, you state its type — a label like int or char that tells the compiler two things at once: what kind of value this is (a whole number, a single character, a number with a fraction) and exactly how many bytes of memory to set aside for it. A byte is the smallest unit of memory a computer addresses on its own — eight bits, each bit a single 0 or 1. Once the compiler knows a variable's type, it knows its size before your program ever runs, and it reserves exactly that much memory and not one byte more.

This is the same trade-off you have met twice already in this course: C hides less, and asks more of you, in exchange for control. Fixed sizes are not a limitation the language forgot to remove — they are what let C run predictably on everything from a smartwatch to a server, and what let you, later in this course, reason exactly about how much memory your own programs use.

Picture packing boxes for a move. One approach is to grab a box whenever you need one and tape more together mid-carry if a box turns out too small — flexible, but you never know how many boxes you have until moving day arrives. C's approach is closer to measuring every item first and choosing an exact box size for it in advance: more work up front, but you know precisely how many boxes the truck needs before you load a single one. A type declaration is that upfront measurement — you are telling the compiler, before your program runs a single line, exactly how much room this value will ever need.

This chapter is about what that bargain actually looks like: the four basic types every C program reaches for first, what sizeof can and cannot promise you about them, and what happens when a value tries to outgrow the size it was given.

Every value in C has a type, and that type fixes both what kind of data it holds and exactly how many bytes of memory it takes up.

How it works

Declaring a variable

A variable is a named piece of memory that holds a value your program can read and change while it runs. Before you can use one in C, you must declare it: state its type, then its name, then a semicolon.

int age;
age = 30;

The first line reserves enough memory for one whole number and names that memory age. The second line stores 30 into it. You can also combine both steps into one line — this is called initialization, and it is the more common style, since it never leaves a variable holding an unknown value even for one line:

int age = 30;

A variable's name follows the same rules as any other name in C: letters, digits, and underscores only, and it cannot start with a digit. age, total_score, and _count are all valid names; 1st_place is not. Names are case-sensitive, so age and Age are two different variables. You can declare several variables of the same type on one line, separated by commas:

int width = 10, height = 20, area;
area = width * height;

A variable declared without a value — int age; on its own — does not start at 0. It holds whatever bits were already sitting in that memory from whatever ran before your program, an indeterminate value. Reading it before you assign something real is a common source of bugs that seem to work by accident on one run and print nonsense on the next. Always initialize a variable before you read it.

Once declared, a variable can be reassigned as many times as your program needs. Assigning a new value does not change its type or its size — only what is stored in the same fixed slot of memory:

int score = 0;
score = 10;
score = score + 5;   /* score is now 15 */

Where you declare a variable also decides how long it lives and where it can be seen. A variable declared inside a function's { } block — the only kind you have written so far — only exists while that block is running, and only code inside that same block can refer to it by name. Two different functions can each declare a variable named total without conflict, because each one lives inside its own separate block and neither can see the other's. Module 3 covers this properly, under the name scope; for now, the rule you need is simpler: a variable you declare inside main's braces belongs to main, and disappears the moment main finishes.

int — whole numbers

int holds a whole number — no fraction, positive or negative. It is the type you will reach for most often in this course. C guarantees an int can hold at least the range -32767 to 32767, though on every platform this course targets, the real range is far larger — you will measure it yourself in the "Asking sizeof" section below.

int supports the arithmetic you would expect: +, -, * for addition, subtraction, and multiplication. Division, written /, has a trap worth learning now rather than the hard way later:

#include <stdio.h>

int main(void) {
    int total = 7;
    int people = 2;
    int share = total / people;

    /* %d tells printf to print a whole number here — next chapter
       covers every format specifier printf understands. */
    printf("%d\n", share);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror int_division.c -o int_division
$ ./int_division
3

7 / 2 is mathematically 3.5, but int division in C throws away the fraction instead of rounding — 7 / 2 is 3, not 4 and not 3.5. This is called truncation: the result is always cut toward zero, never rounded. If you need the leftover, C gives you a separate operator for it, % — the modulo operator, which reports the remainder: 7 % 2 is 1. Dividing two ints always throws away the fraction, no matter how the result is used afterward — this is exactly why the "Fractional numbers" section below exists.

Modulo has one more sharp edge worth knowing before you rely on it: what happens when one side is negative. C guarantees that a / b truncates toward zero — rounds toward 0, not down toward the smaller number — and that a % b always satisfies (a / b) * b + (a % b) == a. Put those two guarantees together and -7 % 2 works out to -1, not 1: the sign of the remainder follows the sign of the number being divided, not the divisor. This trips people up the first time they use modulo to "wrap" a count into a fixed range, since a negative input produces a negative result instead of the positive one they expected.

char — single characters

char holds one character — a letter, digit, punctuation mark, or space. A character literal is written in single quotes, 'A', which is different from a string literal in double quotes, "A", which you met in chapter 1.1. 'A' is one character; "A" is text — a whole different kind of value you will study properly in Module 4.

Underneath, a char is really a small whole number. Every character your keyboard can produce is assigned a number by a standard called ASCII (American Standard Code for Information Interchange) — 'A' is 65, 'a' is 97, '0' is 48, and so on through the rest of the keyboard. A char variable stores that number; printing it with the right format specifier decides whether you see the character or the number:

#include <stdio.h>

int main(void) {
    char letter = 'A';

    /* %c prints the character; %d prints the number underneath it —
       same variable, same bits, two different ways to read them. */
    printf("%c\n", letter);
    printf("%d\n", letter);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror char_as_number.c -o char_as_number
$ ./char_as_number
A
65

Because a char is a number underneath, you can do arithmetic on it. The digit characters '0' through '9' are assigned consecutive numbers in ASCII, so subtracting '0' from any digit character converts it to the whole number it represents:

char digit = '7';
int value = digit - '0';   /* value is now the int 7, not the char '7' */

This is the exact idea behind this chapter's first exercise. It works because ASCII assigns '0' through '9' consecutive numbers in order, so the distance between any digit character and '0' always equals the digit it represents.

Whether a plain char can hold negative numbers depends on the compiler and platform — some treat it as always non-negative (an unsigned type), others allow negatives (a signed type). This rarely matters for ordinary letters and digits, since their ASCII numbers are always positive and small. It becomes a real trap only if you use a plain char to store raw byte values above 127 and then compare or arithmetic on it — code that silently behaves differently on two machines. When that distinction matters, C gives you signed char and unsigned char to say exactly which one you mean.

Fractional numbers: float and double

When a value needs a fraction — a price, a temperature, an average — int cannot hold it. C gives you two floating-point types for this: float and double. Both store a number with a decimal point; the difference between them is precision and size, covered in the next section. Use double unless you have a specific reason to reach for float — it is this course's default, and the more common choice in real C code.

#include <stdio.h>

int main(void) {
    double total = 7.0;
    double people = 2.0;
    double share = total / people;

    /* %f prints a floating-point number. */
    printf("%f\n", share);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror float_division.c -o float_division
$ ./float_division
3.500000

Notice the .0 on both literals. 7 / 2 is int division and truncates to 3, as the last section showed — even if the result is later stored in a double. Only 7.0 / 2.0, where at least one side is already a floating-point value, performs floating-point division and keeps the fraction. This is precisely the trap this chapter's second exercise is built around: averaging whole numbers correctly means making sure the division itself happens as floating-point, not after the fact.

A floating-point number is stored in binary, and most decimal fractions — including something as ordinary as 0.1 — cannot be represented exactly in binary, the same way 1/3 cannot be written exactly as a finite decimal. The value stored is the closest one that fits, off by a tiny amount. That tiny amount is usually invisible, but it means two floating-point values that "should" be equal mathematically can differ in their last few digits. Never compare floating-point numbers with ==. Instead, check that the difference between them is smaller than some tiny tolerance you choose — this is exactly what this chapter's average test does, instead of comparing an exact number.

That imprecision is not a rumor — you can print it yourself. Ask printf for more digits than 0.1 actually needs, and the ones after where a person would stop reveal the real, imperfect value sitting in memory:

#include <stdio.h>

int main(void) {
    double value = 0.1;

    printf("%.20f\n", value);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror float_imprecision.c -o float_imprecision
$ ./float_imprecision
0.10000000000000000555

0.1 printed with 20 digits after the point is not 0.1 at all — it is the closest binary fraction to 0.1, and the two are not the same number. printf normally rounds this away before showing it to you, which is exactly why the gap stays invisible until you go looking for it, or until you add up enough of these tiny errors that they stop being invisible.

float exists for the same reason fixed sizes exist at all: it uses less memory than double, at the cost of less precision — roughly 7 accurate decimal digits, against double's roughly 15. A float literal needs an f suffix to tell the compiler which type you mean, since a plain decimal literal like 3.5 is a double by default:

float price = 3.5f;
double precise_price = 3.5;

Asking sizeof

You do not have to guess how many bytes a type uses — C has an operator that reports it directly: sizeof. It takes a type or a variable and reports its size in bytes, as a special unsigned whole-number type called size_t, printed with the format specifier %zu:

#include <stdio.h>

int main(void) {
    printf("char:   %zu\n", sizeof(char));
    printf("int:    %zu\n", sizeof(int));
    printf("float:  %zu\n", sizeof(float));
    printf("double: %zu\n", sizeof(double));
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror sizeof_demo.c -o sizeof_demo
$ ./sizeof_demo
char:   1
int:    4
float:  4
double: 8

Those exact numbers — 4 for int, 8 for double — are what every common desktop and laptop platform reports today, and what this course's reference solutions rely on. But "predict sizeof" does not mean "memorize one universal number." The C standard only guarantees a smaller set of facts, and the difference matters:

  • sizeof(char) is always exactly 1, by definition — the standard defines a byte as the size of a char, so this one never varies.
  • sizeof(char) <= sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long) — each integer type is guaranteed to be at least as large as the one before it, never smaller, but the standard does not guarantee they are all different sizes.
  • double is guaranteed to have at least as much range and precision as float, which in practice means it is at least as large. It does not have to be exactly twice the size — that is what today's hardware happens to give you.

Older or more unusual hardware really has shipped C compilers where int was 2 bytes, not 4. This course's tests reflect that honesty: they check relationships like "int is at least 2 bytes" and "double is at least as wide as float," never a single hardcoded byte count for anything except char, the one type the standard actually pins down.

size_t, the type sizeof reports in, is unsigned — it can never hold a negative number, because a size in bytes can never be negative. That sounds harmless until you compare one to an ordinary, signed int that happens to be negative. C's rules quietly convert the signed value to unsigned before comparing, and a negative number converted to unsigned does not become small — it wraps into a huge positive number instead, the same wraparound rule this chapter's next section covers. A check like some_int < sizeof(x) can silently do the opposite of what it looks like it does if some_int is ever negative. You will not need to worry about this yet, but recognize the shape of the mistake now — it resurfaces the moment sizeof starts appearing in real conditions, in Module 4 and beyond.

Why fixed sizes matter

A fixed size is not only bookkeeping for the compiler. It is a hard ceiling on what a value can hold — and hitting that ceiling has real, visible consequences. unsigned char, one byte, can hold whole numbers from 0 to 255 and nothing outside that range. Add 1 to 255, and there is no room left to carry the result up to 256 — so it wraps back around to 0 instead:

#include <stdio.h>

int main(void) {
    unsigned char count = 255;
    count = count + 1;

    printf("%d\n", count);
    return 0;
}
$ cc -std=c17 -Wall -Wextra -Werror wraparound.c -o wraparound
$ ./wraparound
0

This is not a bug in the compiler — it is a rule the C standard actually guarantees for every unsigned type: the result wraps around, predictably, as if the compiler kept only the remainder after dividing by the total number of values the type can hold (256, for one byte). 300 % 256 is 44, and that is exactly what 200 + 100 stored in an unsigned char produces — this chapter's fourth exercise asks you to write that wraparound arithmetic yourself.

A car's odometer is the same idea in a machine you can hold. It has a fixed number of wheels, so it can only display so many digits — once it reaches its highest number, the next mile does not stop the car or crash the dashboard, it rolls every wheel back to zero and starts counting again. Nobody designed the odometer to lie about the car's real mileage past that point; they designed it with a fixed number of wheels because an odometer with infinitely many wheels would be infinitely large. A one-byte unsigned counter is the same trade, in software: fixed room, predictable rollover, and a hard limit on how high it can count before it starts over.

Ordinary int is signed, and overflowing a signed type — the largest possible number, plus one — is not a guaranteed wraparound at all. The C standard calls it undefined behavior: the compiler is allowed to do anything, including produce a value that looks nothing like a wraparound, or optimize your code in a way that assumes it never happens in the first place. Module 14 covers undefined behavior in depth. For now, the rule that matters is narrower and worth remembering on its own: unsigned wraparound is predictable and guaranteed; signed overflow is not, and code that relies on it is already broken even if it happens to print something reasonable today.

Zoom out from the one-byte example and the same idea holds at every size C gives you. A fixed size means a program never has to guess how much memory a value needs, and the computer's own arithmetic hardware — built to work in fixed widths like 8, 16, 32, and 64 bits — can operate on it directly, with no extra bookkeeping. That speed and predictability is the other half of the bargain this chapter's big picture opened with: C trusts you to pick a type big enough for what you actually need, and in return, every value in your program uses exactly the memory you asked for, no more.

Zooming out: from what a value looks like to printing it and reading it back

You can now declare and use int, char, float, and double, predict what sizeof actually guarantees about each of them versus what today's hardware happens to give you, and explain why a fixed size is not a limitation — it is what makes memory use predictable and arithmetic fast. You have also seen the first real cost of that bargain: a value that outgrows its type either wraps around in a well-defined way, if it is unsigned, or invites undefined behavior, if it is signed.

Every code example in this chapter leaned on printf and a handful of format specifiers — %d, %c, %f, %zu — without slowing down to explain each one fully. That was deliberate. Next chapter covers every format specifier printf understands, and introduces scanf, which reads a value the person at the keyboard typed into a variable of your choosing. scanf's biggest trap turns out to be exactly this chapter's subject: telling it the wrong type for the variable you are reading into is a mistake the compiler often cannot catch for you, and it is undefined behavior at runtime — the same danger this chapter's "Why fixed sizes matter" section already showed you, aimed at a new target.

Every later chapter in this course assumes you can look at a declaration — int, char, float, or double — and know immediately what kind of value it holds and roughly how much room it takes up. Arrays of these types (Module 4), pointers to them (Module 5), and structs that group several of them together (Module 6) are all built directly on the four types you have now learned — nothing about them changes once you start combining types into bigger ones.

The four exercises you are about to write already point in that direction, even though the next chapter has not arrived yet. digit_value turns typed input, one character at a time, into a real number — exactly the conversion a program reading someone's age or a menu choice needs. average needs a correctly typed result before it can ever be printed with the right format specifier. Both problems only get more useful once the next chapter lets your program ask a person a question and read back whatever they type.
